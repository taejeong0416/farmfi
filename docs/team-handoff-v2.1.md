# FarmFi v2.1 개정 · 팀별 전달 문서

> 기준일 2026-08-19 · 상위 문서: `FarmFi 기능명세서 v2.1 개정 패치`
> 대상: 백엔드·블록체인, 프론트엔드
> 목적: 이번 개정에서 **각 팀이 실제로 손대는 것**과 **팀 간 계약(API·상태·이벤트)**을 분리해 정리한다.

이번 개정의 무게는 **백엔드·체인 쪽에 거의 다 실린다.** 프론트는 새로 만들 화면이 마일스톤 증빙 2개뿐이고, 나머지는 "만들지 말 것"과 "라벨·잔재 정리"가 중심이다.

바뀐 3가지(요약): ① 토큰을 수탁 지갑 방식으로 발행(화면 비노출), ② 마일스톤 증빙 제출·승인을 P0로, ③ 자금 보관은 신탁만("에스크로" 용어 삭제, 출시 시 적용).

# PART 1 · 백엔드 · 블록체인

## 1-A. 할 일 체크리스트

### 수탁 지갑 · 토큰 발행 (신규 핵심)

- [ ] 투자자 1인당 BESU **수탁 지갑** 생성·관리 (`CustodyWallet`). 키는 KMS/HSM, 평문 저장 금지.
- [ ] 컨트랙트에 `HoldingLedger` 모듈 추가: `mintHolding` / `transferHolding` / 조회.
- [ ] `InvestmentAgreement`에서 "토큰 발행·전송 없음" 삭제 → 입금 확인 시 `HoldingLedger`에 발행 요청.
- [ ] `**confirmDeposit` 성공 직후 같은 Outbox 처리 안에서 `mintHolding` 호출을 이어 붙임.** 파이프라인 신설 아님 — 기존 9.4 흐름에 한 스텝 추가.
- [ ] 발행·이전도 `eventId` 멱등, 프로젝트 상태 검사, 이벤트 발생 구현.
- [ ] 회수 완료·환불은 삭제가 아니라 반대 이벤트(transfer/burn)로 처리.
- [ ] 1구좌 = 1만 원, 정수 단위(소수점 없음). 100만 원 → 100구좌.

### 마일스톤 증빙 게이트 (P0로 승격)

- [ ] `submitEvidenceHash`(운영자) / `approveMilestone`(관리자) 경로 MVP로 구현.
- [ ] **증빙이 `APPROVED`가 아니면 집행 가능액 확정(집행 승인)을 생성하지 않음.** ← 조건부 집행의 핵심.
- [ ] 이의제기·외부 전문가 판정(O-11E·A-09)은 후속(P2)으로 남김.

### 자금 보관 (용어·어댑터)

- [ ] `FundCustodyAdapter` 신설, 데모는 Mock. 출시 시 신탁사 연동.
- [ ] 코드·주석·로그에서 **"에스크로" 단어 쓰지 않음.** 자금 분리보관은 "신탁(custody)"으로 표기.

### 데이터 모델 추가

- [ ] `CustodyWallet(walletId, investorId, chainAddress, keyRef, status, createdAt)`
- [ ] `HoldingIssuance(issuanceId, investmentId, walletId, units, method, chainTxHash, status, occurredAt)`
- [ ] `keyRef`는 KMS/HSM 참조값. 계좌·키 원문 저장 금지. 체인엔 해시·내부식별자만.

### 권한·경로

- [ ] `mintHolding`·`transferHolding`은 **Chain Relay(운영키)만** 호출. 투자자 개인키 서명 없음.
- [ ] 프론트·투자자가 발행·이전을 직접 호출하지 못하게 차단.

## 1-B. 안 할 일 / 주의

- 투자자에게 개인키 서명 요구 금지 (수탁 구조라 서명 주체는 팜피 운영키).
- 체인이 현금을 쥐지 않음 — 원화는 은행/PG로만.
- 관리자 수기 체인 기록 API 만들지 않음 — 반드시 도메인 이벤트 경유.

## 1-C. 프론트에 넘겨줘야 할 것 (계약 — PART 3에서 상세)

- 신규 상태값 2개(`chainStatus`에 발행 단계 포함), 회수/보유를 "투자 금액·보유 구좌"로 내려주는 응답 형태.
- **화면에 토큰·주소·잔액을 절대 안 내려보냄.** 프론트가 그릴 게 없도록 응답에서 원장 원문 제외.

## 1-D. 확인 필요 (블로커)

- [ ] **Chain Relay / `mintHolding` / 마일스톤 게이트가 지금 코드에 실제로 도는가?**
  - 돈다 → 아래 계약 그대로.
  - 아직이다 → `HoldingLedger`·`FundCustodyAdapter`를 "신규 구현" 트랙으로, 발표·문서엔 "개발 중" 표기.

# PART 2 · 프론트엔드

## 2-A. 할 일 체크리스트

### 새로 만들 화면 (P0로 올라온 것)

- [ ] **O-11 · 운영자 마일스톤 증빙 제출** (기존 Phase 2 → MVP).
- [ ] **A-08 · 관리자 증빙 검토·승인** (기존 Phase 2 → MVP).
- [ ] O-11E(이의제기)·A-09(외부 판정)는 후속 — 지금 안 만듦.

### 라벨·잔재 정리

- [ ] **C-I03(본인 계좌 확인)** 안의 옛 지갑 레이어 이름 정리: `공식 앱 안내 / 설치 순서 / 스토어 버튼` → `계좌 입력 카드 / 확인 순서 / 계좌 액션 버튼`. 표시 텍스트는 이미 계좌 확인이 맞음(이름만 잔재).
- [ ] I-07(보유 투자)에서 `보유 수량·토큰` 영역 제거 → "투자 금액 / 보유 구좌 / 계약 상태"로 대체.
- [ ] 프로젝트 상세 등에서 `토큰 이전·중도 환매`, `락업`, `토큰 배정 예정` 문구 잔재 제거.

### 삭제/차단

- [ ] `DEPRECATED · 지갑 주소 등록`(node 10:503), `DEPRECATED · 지갑 재연결`(node 10:968) 라우팅에서 제외. 기존 URL 접근 시 C-I03 또는 C-I05로 리다이렉트.

### 자금 표기

- [ ] 투자금 관련 화면에 신탁 표기가 필요하면 "분리보관 · 출시 시 신탁 적용"으로만. "에스크로" 쓰지 않음.

## 2-B. 안 만들 것 (중요)

- **토큰·수탁 지갑 UI를 새로 만들지 않는다.** 주소·개인키·가스비·토큰 잔액 화면 없음.
- 토큰은 백엔드·체인 안에서만 발행됨 — 프론트는 그 존재를 화면에 드러내지 않음.
- 보유는 오직 "투자 금액 / 보유 구좌"로만 표현.

## 2-C. 용어 (0.4 그대로 — 재확인)

STO·토큰증권·토큰 배정·배당·지갑설치·체인주소 → 화면에서 금지. 대신 프로젝트 투자 / 투자 금액·보유 구좌 / 회수금·지급 예정액 / 모바일 신분증 확인·본인 계좌 확인 / 등록 계좌로 지급.

## 2-D. 확인 필요

- [ ] O-11·A-08 화면이 와이어프레임에는 Phase 2 존에 그려져 있음 — **존 위치와 무관하게 MVP로 구현.** 디자인 소스 위치만 옮기면 됨(기능은 P0).

# PART 3 · 팀 간 계약 (API · 상태 · 이벤트)

이 부분이 두 팀이 서로 기다리는 지점이다. 여기 규격만 합의되면 병렬로 진행 가능.

## 3-A. 투자 신청 상태 흐름 (발행 단계 포함)

```
DRAFT → IDENTITY_REQUIRED → ELIGIBILITY_CHECKED → CONSENT_REQUIRED
→ AWAITING_DEPOSIT → DEPOSIT_CONFIRMED → CHAIN_PENDING → COMPLETED
```

- `CHAIN_PENDING` 구간에서 백엔드가 하는 일: 계약·입금 해시 기록 **+ 수탁 지갑에 구좌 발행(mint)**.
- 프론트 표기: 이 구간은 여전히 "입금 확인 완료 · 기록 처리 중"으로만 보여줌. **발행이라는 단어를 화면에 쓰지 않음.**
- 예외: `CHAIN_FAILED`(기록·발행 실패, 재시도 대상). 은행 입금은 취소하지 않음.

## 3-B. 보유/회수 응답 계약

프론트는 아래 필드만 받는다. 원장 원문(주소·txHash·토큰수량)은 내려보내지 않는다.

- 보유(내 투자): `{ projectId, amountKRW, units(구좌수), contractStatus, milestoneProgress }`
- 회수: `{ period, expectedPayoutKRW, paidKRW, failedKRW, calcBasis, payoutAccountMasked }`
- 금지: `walletAddress`, `privateKey`, `gasFee`, `rawTokenBalance` — 응답 스키마에 존재하지 않음.

## 3-C. 마일스톤 게이트 계약

- 운영자 O-11 제출 → 백엔드 `submitEvidenceHash` → 상태 `EVIDENCE_SUBMITTED`.
- 관리자 A-08 승인 → `approveMilestone` → `APPROVED`.
- `**APPROVED`가 아니면 집행 API가 거부.** 프론트는 미승인 단계의 집행 버튼을 비활성.
- 상태값: `SCHEDULED → EVIDENCE_SUBMITTED → REVIEWING → APPROVED → EXECUTION_REQUESTED → PAID` (+ `REVISION_REQUIRED` 등 예외).

## 3-D. 관여 API (신규·변경만)

신규:

- `POST /investments/{id}/holdings` (내부용, Chain Relay 트리거 — 프론트 직접 호출 아님)
- `GET /me/investments/{id}` 응답에 `units` 포함 (보유 구좌)

기존 유지: 본인확인·계좌·프로젝트·투자·구독·운영자·관리자 엔드포인트는 v2.0 그대로.

## 3-E. 원칙 (애매하면 여기로)

1. 현금은 은행/PG로만 이동, 체인은 현금 안 쥠.
2. 체인 쓰기는 Chain Relay 한 곳만.
3. 서버 상태가 단일 진실 공급원, 체인 기록은 비동기로 뒤따름.
4. 화면에는 STO·토큰·지갑 노출 안 함.
