# QA

`web-qa-sheet.xlsx` — 웹(`frontend/`) QA 시트. 5탭이다.

| 탭 | 내용 |
|---|---|
| 대시보드 & 엄수 규칙 | 라운드·배포 커밋·기준 문서·집계 수식 · 명세 18장 인수 테스트 판정 · 이 시트가 못 잡는 것 |
| TC 시나리오 | 케이스별 시나리오·기대 결과·판정. `라운드` 열로 1·2·3차를 나눈다 |
| 요청사항(REQ) | Fail 로 등록한 이슈. 심각도·재현·증거·해결 방향과 실제 수정 커밋 |
| 공통 TC 크로스 | 전 화면에 걸리는 공통 기준의 라운드별 결과 |
| 기능 기준표 | 기능 ID ↔ 기대 동작. 근거는 `feature-spec.md` 조항 |

## 어떻게 만들었나

배포본(`https://farmfi.co.kr`)을 Playwright(Chromium)로 직접 조작하고 API 를 직접 호출했다.
읽기만 하지 않고 청약·증빙 제출·마일스톤 승인 같은 쓰기 경로까지 실행했으며, 끝난 뒤
`/api/demo/reset` 으로 시드를 복구했다. 기대 결과는 `feature-spec.md` 에서 가져왔고, 명세가
정하지 않은 화면은 케이스를 만들지 않았다.

라운드는 셋이다. 1차는 수정 전 프로덕션, 2차는 수정 반영 후 로컬 dev, 3차는 그 코드를 배포한 뒤
같은 TC 를 배포본에서 다시 돌린 것이다. 앞 라운드 판정은 덮어쓰지 않고 행을 새로 쌓는다 —
무엇이 깨져 있었는지가 기록에서 사라지면 같은 자리를 다시 깨뜨린다.

라운드마다 배포 커밋 SHA 를 시트 머리에 적는다. 1차 QA 중 세션 도중 재배포가 있었고 같은 TC 가
다른 코드를 봤다(REQ-009).

## 다시 돌리기

읽기 전용 26건은 스크립트 하나다. 시드 계정으로 로그인만 하고 아무것도 쓰지 않는다.

```
cd frontend && node scripts/qa-prod-round.mjs
```

쓰기 경로 10건(TC-X14~X20 · Y09 · Y10 · Z02)은 스크립트에 없다. 배정 관계를 바꿔 403 을 보고,
청약 한 건을 만들어 지급사 웹훅 규약대로 입금 통지를 쏘고, 끝나면 리셋으로 되돌리는 절차라
픽스처 준비와 사후 대조에 DB 접근이 필요하다.

입금 TC 를 로컬에서 재현할 때는 경로가 다르다. 로컬은 Mock 어댑터라
`/api/webhooks/bank/deposits` 를 쓰고, 프로덕션은 토스 어댑터라 `/api/webhooks/toss/deposits` 에
계좌별 secret 을 실어 보낸다.
