## A. 개발 단계에서 쓴 AI

### 1. 도구


| 도구                      | 쓴 곳                                                                                                                                         | 범위                       |
| :----------------------- | :------------------------------------------------------------------------------------------------------------------------------------------- | :------------------------ |
| Claude Code (Anthropic) | `frontend/` 화면·API 라우트·도메인 로직·Prisma 스키마·시드, `contracts/` 컨트랙트, `app/` 운영자 앱, `tools/figma` 대조 스크립트, `frontend/scripts` QA 스크립트, `docs/` 문서 | 코드 생성·리팩터링·테스트·문서 작성     |
| Claude Code 멀티에이전트 리뷰   | 변경분 코드리뷰                                                                                                                                    | 리뷰 에이전트 병렬 실행 + 발견 건별 반증 |


### 2. 활용 범위

**AI가 쓴 것** — 화면 컴포넌트, API 라우트, 도메인 계산 로직(청약·정산·최적화)의 초안,
단위 테스트, 문서. 커밋 446건 중 대부분의 코드 라인이 AI 생성 초안에서 출발했다.

**사람이 정한 것** — 무엇을 만들지와 어떤 값이 맞는지다. 화면 62개 목록과 순서
(`build-plan.md`), 색·좌표·폰트(`design/*.fig`가 기준), 도메인 규칙(트랜치 집행 조건,
"확정 발행 합 == 청약 합" 같은 불변식), 스키마 설계, 배포 구성.

**AI에 맡기지 않은 것** — 운영 키·계정 발급(Supabase·Vercel·토스페이먼츠·OACX),
프로덕션 DB에 대한 파괴적 작업, 실물 결제·본인확인 경로의 최종 판정.

### 3. AI 생성 코드의 검증·수정 방식

네 겹으로 걸렀다. 위로 갈수록 싸고 자주, 아래로 갈수록 비싸고 늦게 돈다.

**(1) 타입·테스트** — `tsc --noEmit`으로 전체 타입 통과를 확인하고 도메인 계산은
단위 테스트로 고정했다(`frontend/src/**/*.test.ts` 15개 파일, `npm test`).
로컬 `next build`는 한글 경로에서 readlink EISDIR로 깨져서 렌더 확인은 `next dev`로 하고
프로덕션 빌드는 Vercel(Linux)에서 받는다.

**(2) 도면 대조 (기계)** — AI가 만든 화면이 Figma와 얼마나 벌어졌는지를 사람 눈 대신
스크립트로 센다. `tools/figma`의 `labels.py`+`audit.mjs`가 "그 문구가 화면에 있는가",
`geometry.py`+`geometry.mjs`가 "어디에, 얼마나 크게" 있는가를 대조한다. 결과는
`build-plan.md` Phase X·Y에 남고 문구 일치율이 낮으면서 발표 동선에 있는 화면부터 고쳤다.

**(3) 멀티에이전트 코드리뷰** — 변경분을 여러 리뷰 에이전트에 나눠 돌리고 발견 건마다
별도 에이전트가 반증을 시도해 살아남은 것만 채택했다. AI 리뷰가 그럴듯하게 틀린 지적을
내는 것을 거르기 위한 절차다. 피벗분 27건, STO 재융합분 10건의 결함을 이 경로로 잡았다.

**(4) 배포본 수동 QA** — 위 셋을 다 통과한 코드를 실제 배포본에서 사람이 눌러 확인했다.
판정은 `qa/web-qa-sheet.xlsx`에 라운드별로 남기고 라운드마다 기준 배포 커밋을 적는다
(세션 도중 재배포가 있으면 같은 TC가 다른 코드를 보기 때문이다).
읽기 전용 26건은 `frontend/scripts/qa-prod-round.mjs`로 자동화했고 쓰기 경로는 픽스처
준비와 사후 대조에 DB 접근이 필요해 수동으로 둔다.

**수정 방식** — 결함은 고친 뒤 같은 TC를 배포본에서 다시 돌려야 닫는다. 로컬 통과는
닫힘으로 치지 않는다. 결정의 근거는 `dev-log.md`에 남긴다.

**AI 리뷰가 못 잡은 것** — 가장 무거운 결함 두 건은 타입·테스트·AI 리뷰를 전부 통과한 뒤
(4)에서 나왔다. 거래번호가 다른 두 번째 입금이 확정 발행을 중복으로 일으켜
"확정 발행 합 == 청약 합"이 깨진 것(청약 110구좌 / 발행 210구좌), 그리고 시연 데이터
리셋이 실제 가입 계정까지 지운 것이다. 둘 다 코드 한 줄이 틀린 문제가 아니라 상태가 겹칠 때
드러나는 문제여서 정적 검토로는 보이지 않았다. 검증에서 실제 조작 단계를 뺄 수 없는 이유다.

## B. 서비스에 들어간 AI

개발 도구가 아니라 사용자가 쓰는 제품 기능이다. 이 코드도 A-3의 검증 절차를 똑같이 거쳤다.


| 기능         | 쓰는 모델·방식              | 역할                          |
| :---------- | :--------------------- | :--------------------------- |
| 마일스톤 증빙 검증 | Google Gemini 비전·OCR  | 계약서·영수증·현장사진 판독 후 문서 간 교차검증 |
| 생육 이상 탐지   | 센서 Z-score + 도메인 정상범위 | 지속성 고장·스파이크 조기 감지           |
| 판매-재배 최적화  | 판매 추이 회귀              | 다음 재배 사이클 증산/감축 추천          |
| 생육 레시피     | 환경↔수율 반응표면 학습         | 수익 최적 환경조건과 불확실성 구간 산출      |
| 운영 브리핑     | LLM 하네스               | 상황을 보고 필요한 분석 도구를 골라 실행     |


증빙 검증은 자금 집행의 게이트다. AI 판정이 통과하지 않으면 트랜치가 나가지 않고
강제 통과 경로는 없다. provider는 키가 설정된 것만 Gemini → OpenAI → Anthropic 순으로
시도하며 현재 키는 Gemini만 넣어 두었다.

계산의 식·가정·한계는 `optimization-rationale.md`와 `growth-recipe-rationale.md`,
기능 명세는 `feature-spec.md`에 있다.
