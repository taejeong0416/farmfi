# FarmFi 구조 — 설계 근거

이 문서는 FarmFi가 **왜 이런 구조여야 하는지**를 설명한다. 읽고 나면 "투자자 돈이 운영자에게 닿기까지
누가 무엇을 막고 있나", "그 방어선 중 어느 것을 우리가 못 치우나", "이 구조가 아직 증명하지 못한 것은
무엇인가"에 답할 수 있어야 한다.

무엇을 만들지는 `../spec/feature-spec.md`·`../spec/app-feature-spec.md`가, 무엇이 실제로 도는지는
저장소 최상위 `README.md` 3장이 담당한다. 이 문서는 그 사이 — **어떤 위협을 상정했고, 그 위협을 막으려고 무엇을 포기했는가**를
다룬다. 계산 내용은 `optimization-rationale.md`(운영최적화)와 `growth-recipe-rationale.md`(생육 레시피)에
따로 있고, 신원과 서명의 주체 분리는 `identity-and-signing.md`가 다룬다.

§1~§9는 완성 시점의 구조와 그 근거를 기술한다. 지금 구현이 거기 못 미치는 부분은 §10에 모아 뒀다.

## 0. 한 장 요약

**무엇을 만드나.** 도심 유휴공실을 스마트팜 매장으로 바꾸는 자금을 토큰증권(STO)으로 조달하고,
그 자금을 한 번에 주지 않고 **공사·설비·개점이 실제로 이뤄졌다는 증거가 확인될 때마다** 나눠 집행한다.

**왜 이게 구조 문제인가.** "조건이 충족되면 집행한다"는 문장은 누구나 쓸 수 있다. 그 문장을 지키는
주체가 사람이면 지키지 않아도 아무 일이 일어나지 않는다 — 기존 보조금 집행이 그렇다. 이 제품의 기술적
주장은 하나뿐이다. **그 문장이 약속이 아니라 코드여야 하고, 그 코드를 만든 우리조차 우회할 수 없어야 한다.**

**핵심 결정 일곱.** 각 결정은 특정 부정을 겨냥한다.

| 결정 | 무엇을 막나 | 어디 |
|:---|:---|:---|
| 자금을 마일스톤 단위로 쪼갠다 | 받고 잠적 | §2.1 |
| 증거 없이는 집행 상태로 갈 수 없다 | 승인 도장만으로 나가는 돈 | §2.2 |
| 같은 조건을 컨트랙트가 다시 건다 | 우리가 서버를 고쳐서 여는 것 | §2.3 |
| 영수증과 사진을 교차대조한다 | 무관한 사진을 붙이는 위조 | §2.5 |
| 관문마다 탈출구를 짝지어 둔다 | 자금이 영영 묶이는 것 | §2.6 |
| LLM은 알고리즘을 고를 뿐 값을 내지 않는다 | 출처를 댈 수 없는 숫자가 정산에 쓰이는 것 | §3.1 |
| 필요 없는 개인정보는 받지 않는다 | 보관한 적 없는 값의 유출 | §4.2 |

**한 문장으로 규정하면.** 판단은 결정론적 코드가 하고, LLM과 사람은 그 판단을 **호출·통역**할 뿐이다.
이 원칙이 §2(집행 게이트)·§3(AI)·§7.3(계산 계층) 세 곳에서 같은 모양으로 반복된다.

**정직하게 밝히는 범위.** 이 구조에서 실제로 검증된 것은 "Mock 외부사업자를 물린 상태에서 흐름 전체가
돈다"까지다. 은행·PG·신탁은 전부 어댑터 뒤의 Mock이고, 학습 스택은 실 수확 라벨이 0건이다. §10이
그 경계를 항목별로 적는다.

## 1. 문제 설정

### 1.1 등장인물 다섯과 돈이 도는 방향

| 누구 | 무엇을 내놓나 | 무엇을 얻나 |
|:---|:---|:---|
| 임대인 | 비어 있는 상가 | 임대료 |
| 투자자 | 전환 자금 | 회수금 |
| 운영자 | 노동·운영 | 매출 100% |
| 구매자 | 구매 대금 | 농산물 |
| 관리자 | 예외 처리 | — |

```
투자자 ──자금──▶ [신탁 보관]
                     │
                     │ 마일스톤 통과 시마다 조각 집행      ← §2
                     ▼
                 운영자 (공사·설비·개점 → 매장 운영)
                     │
                     │ 매출 100%는 운영자 것.
                     │ 운영자는 FarmFi에 이용료를 낸다
                     ▼
              FarmFi 수수료 풀
                     │
                 60% ├──▶ 투자자 회수금                   ← §5
                 40% └──▶ FarmFi 운영
```

**이 그림에서 한 곳만 기억하면 된다 — 회수금이 운영자 매출에서 나오지 않는다.** 매출에서 떼면 장사가
잘 될수록 뜯기는 구조가 되어 운영자가 애초에 들어오지 않는다. 왜 이 한 단계를 끼웠는지는 §5.1이 다룬다.

### 1.2 왜 조건부 집행이 어려운 문제인가

자금집행을 조건부로 만들려는 시도는 셋 중 하나로 무너진다.

**① 조건 판정을 사람이 한다.** 운영자가 사진을 올리고 관리자가 승인 도장을 찍는 구조는 조건이 아니라
절차다. 도장 찍는 사람이 안 찍거나 잘못 찍어도 시스템은 그걸 모른다.

**② 조건을 코드로 짜되 그 코드를 우리가 고칠 수 있다.** 서버 코드에 게이트를 걸어도 배포 권한이 있는
쪽이 조건을 바꿀 수 있으면, 투자자 입장에서는 도장과 다를 게 없다. 신뢰의 대상이 사람에서 회사로
옮겨갔을 뿐이다.

**③ 조건을 못 고치게 만들었더니 자금이 갇힌다.** 컨트랙트에 조건을 못박으면 우리도 못 푼다. 운영사가
사라지거나 판정이 불가능한 상황이 오면 투자금이 영영 나오지 못한다.

**이 셋이 서로 대립한다는 게 문제의 본질이다.** ①을 피하려면 코드로 가야 하고, ②를 피하려면 못 고치게
해야 하고, 그러면 ③이 온다. §2가 이 삼각형을 어떻게 처리했는지를 다룬다.

### 1.3 이 구조가 상정한 부정 목록

방어선을 설계하려면 무엇으로부터 방어하는지 먼저 적어야 한다. 아래 여섯이 이 문서 전체의 축이다.

| # | 부정 | 막는 곳 |
|:--|:---|:---|
| ① | 자금을 받고 공사를 하지 않는다 | §2.1 마일스톤 분할 |
| ② | 증빙 없이 집행 상태를 만든다 | §2.2 서버 게이트 3중 확인 |
| ③ | 운영사가 코드를 고쳐 조건을 연다 | §2.3 온체인 게이트 |
| ④ | 남의 영수증·사진을 짜깁기한다 | §2.5 교차검증 |
| ⑤ | 지갑을 여러 개 만들어 양도제한을 우회한다 | §4.3 1지갑=1신원 |
| ⑥ | 배당 발표 후 사서 배당만 받고 판다 | §5.5 스냅샷 배당 |

여기 없는 위협은 이 구조가 막지 못한다. §10.1이 그 목록이다.

## 2. 집행 게이트 — 이 제품의 중심

자금이 나가는 경로는 하나뿐이고, 그 앞에 관문 셋을 겹친다. §1.2의 삼각형을 이렇게 처리했다 —
**조건을 코드로 짜되(①), 그 코드를 두 층에 두어 하나는 우리도 못 고치게 하고(②), 못 고치는 층마다
탈출구를 짝지어 둔다(③).**

### 2.1 왜 한 번에 주지 않나

집행 단위를 마일스톤으로 쪼갠 이유는 단순하다. 전액을 선지급하면 그 순간부터 이 제품은 아무것도
통제하지 못한다. 쪼개면 **각 조각마다 "그 조각을 받을 자격이 생겼는가"를 다시 물을 수 있다.**

상태 기계는 이렇다.

```
pending ─┬─→ evidence_submitted ─→ verified ─→ completed
in_progress                ↑           │
         revision_required ┴───────────┘
                           manual_review
                           failed
```

| 상태 | 화면 표기 | 뜻 |
|:---|:---|:---|
| `pending` | 예정 | 아직 시작 안 함 |
| `in_progress` | 진행중 | 직전 단계가 집행되어 열린 단계 |
| `evidence_submitted` | 증빙 제출됨 | 판정 대기 |
| `manual_review` | 보류 | 자동 판정 불가 — 사람이 본다 |
| `revision_required` | 보완 요청 | 증빙 재제출 필요 |
| `verified` | 통과 | 집행 가능 |
| `completed` | 집행 완료 | 자금이 나갔다 |
| `failed` | 실패 | 마감 |

**`verified`에 이르는 길은 둘뿐이고 둘 다 증빙 제출이 전제다** — AI 검증 통과, 또는 관리자 승인.
증빙 없이 집행되는 구간을 하나라도 남기면 "조건 충족 시에만 집행"이라는 이 제품의 근거가 사라진다.

집행 비율은 컨트랙트 생성자에서 basis point로 못박고(`require(totalPct == 10000)`) 나중에 바꿀 함수를
두지 않았다. **투자 후에 집행 비율이 바뀌면 투자 판단의 근거가 사라지기 때문이다.**

### 2.2 서버 게이트 — 상태값 하나를 믿지 않는 이유

`canRelease()`가 자금이 나가는 마지막 서버 관문이다. 확인 항목이 셋이다.

| 확인 항목 | 없으면 |
|:---|:---|
| `status === "verified"` | "증빙이 승인된 단계만 집행할 수 있습니다" |
| `evidenceSubmittedAt` | "운영자 증빙이 없는 단계는 집행할 수 없습니다" |
| `reviewedAt` 또는 `aiVerificationResult` | "증빙 판정 기록이 없습니다" |

**세 번째가 이 게이트의 존재 이유다.** 상태값만 `verified`인 행은 수동 조작이나 마이그레이션 잔재로
생길 수 있다. 그런 행 하나가 통과하면 게이트가 아무것도 막지 못한 게 된다. 그래서 "그 상태에 이르렀다는
기록"을 상태값과 별도로 요구한다.

같은 이유로 `canRunVerification()`은 **검증 신호가 하나도 정의되지 않은 단계를 막는다.** 신호 배열이
비어 있으면 `every`가 공허참으로 통과해 버린다. 조건이 없는 것과 조건을 만족한 것을 코드가 구분하지
못하는 자리라, 명시적으로 막았다.

`canReview()`가 `verified`도 되돌릴 수 있게 열어 둔 것은 반대 방향이다. 증빙 없이 verified가 된 옛
데이터를 보완 요청으로 되돌릴 길이 없으면 그 단계는 집행도 회수도 못 하는 상태로 영영 남는다.

### 2.3 왜 온체인까지 가나

같은 조건을 `Escrow.sol`이 다시 건다.

```solidity
function releaseTranche(uint256 seq) external nonReentrant {
    require(!projectFailed, "Project failed");
    require(seq == currentMilestone, "Wrong sequence");      // 순서를 건너뛸 수 없다
    require(milestones[seq].verified, "Not verified");       // 검증 없이는 못 나간다
    require(!milestones[seq].released, "Already released");  // 두 번 못 받는다
    require(roundGate == address(0) || IRoundGate(roundGate).isOpen(address(this)),
            "Round gate closed");
    ...
}
```

**서버 게이트만으로 충분하지 않은 이유는 §1.2의 ②다.** 서버 코드는 우리가 고칠 수 있다. 배포 권한이
있는 쪽이 조건을 바꿀 수 있으면 투자자가 신뢰해야 할 대상은 코드가 아니라 우리 회사다. 컨트랙트는
배포 후 우리도 못 고친다. **투자자가 우리를 믿지 않아도 성립하는 층이 하나는 있어야 한다.**

두 함수를 나눈 것도 같은 맥락이다. `verifyMilestone(seq, passed)`은 `VERIFIER_ROLE`만 부를 수 있지만
`releaseTranche(seq)`는 **권한 제한이 없다.** 누구나 부를 수 있고 조건이 전부 충족돼야 통과하며 자금은
언제나 생성자에 못박힌 `operator` 주소로만 간다. 집행에 권한을 걸면 그 권한자가 사라졌을 때 검증을
통과한 자금이 묶인다. 검증과 집행이 분리돼 있어 **"검증은 했는데 집행은 안 한" 상태가 온체인에 그대로
보인다는 것**도 의도한 성질이다.

`setRoundGate`가 `currentMilestone == 1 && !milestones[1].released`를 요구하는 것도 마찬가지다 —
**자금이 움직이기 시작한 뒤에 게이트를 끼워 넣을 수 없다.**

### 2.4 판정 불가와 반려를 가르는 이유

`manual_review`를 별도 상태로 둔 것은 편의가 아니다. 센서가 결측이거나 설비가 무응답이면 그건 "조건
미충족"이 아니라 **"판정할 수 없음"**이다. 둘을 같은 상태로 접으면 운영자가 자기 잘못이 아닌 일로
집행을 못 받는다.

이 구분이 §9의 원칙 ①("판정할 수 없으면 판정하지 않는다")의 원형이고, 대사 불일치(§5.6)·설명력 부족·
외기 데이터 부재에서 같은 모양으로 반복된다.

AI 오판정이 최종 판정이 되지 않게 하는 경로도 짝으로 둔다.

```
open(접수) → under_review(운영팀 검토) → escalated(외부 전문가) → approved / rejected
```

외부 전문가는 별도 계정 역할이 아니다(`Role`에 `auditor`가 없다). `escalated`에서 운영팀이 전문가
의견을 `authorRole="auditor"` 코멘트로 대신 기록한다. **역할을 늘리지 않고 기록만 늘린 선택**이라,
실제 외부 감사인을 붙이려면 이 자리를 다시 봐야 한다(§10.2).

### 2.5 교차검증 — 영수증만으로도 사진만으로도 안 된다

`POST /api/milestones/[id]/verify`가 마일스톤의 `requiredSignals`를 순회한다.

| 신호 | 무엇을 보나 |
|:---|:---|
| `contract` | 공간사용 협약서 — 당사자·기간·주소 |
| `receipt` | 설비 영수증 — 구매 항목·금액 |
| `photo` | 현장 사진 — 검출 객체 |
| `iot` | 센서 스트림 — 설비가 실제로 도는가 |

**신호를 늘린 것만으로는 위조가 막히지 않는다.** 영수증만 보면 "샀다"까지고, 사진만 보면 "있다"까지다.
둘 다 제출하되 서로 무관해도 각각은 통과한다.

그래서 영수증의 구매 항목과 사진의 검출 객체가 **같은 설비 카테고리를 하나 이상 공유**하는지 확인한다.
카테고리는 조명(led/light/lamp) · 센서 · 재배설비(선반/베드/rack) · 관수(펌프/양액/irrigation) 넷이다.
둘을 교차하면 **"산 것이 거기 있다"**가 되고, 영수증과 무관한 매장 사진을 붙이는 가장 단순한 위조가
여기서 걸린다.

**검증 라우트를 admin 전용으로 둔 것은 임시방편이다.** 신탁 자금 집행으로 이어지는 경로인데 `Project`에
소유자 필드가 없어 "내 프로젝트만"을 강제할 수 없다. 누구나 스스로 operator가 되어 남의 프로젝트를
집행하는 권한 자가상승을 admin 게이트로 막고 있다. 소유자 모델이 들어오면 이 게이트는 좁혀야 한다(§10.2).

내부 self-fetch에도 호출자의 `Authorization` 헤더 또는 쿠키를 그대로 넘긴다. base URL은
`NEXT_PUBLIC_BASE_URL`이 아니라 **현재 요청의 origin**을 쓴다 — `NEXT_PUBLIC_*`은 빌드 타임에
인라인되므로 로컬 `.env`의 `localhost:3000`이 프로덕션 번들에 구워질 수 있다. 실제로 그렇게 죽은 적이 있다.

### 2.6 관문을 세게 걸수록 탈출구가 필요하다

§1.2의 ③이 여기서 온다. 조건을 못 고치게 만든 대가로 **자금이 영영 못 나가는 상태**가 새 위험이 된다.
관문마다 짝을 지었다.

| 장치 | 무엇을 막나 |
|:---|:---|
| `MILESTONE_TIMEOUT = 180 days` | 운영사가 실패 선언을 미뤄 자금이 동결되는 것 |
| `triggerTimeoutFailure()` — 누구나 호출 | admin 선의에 의존하는 구조 |
| `refund()` — 지분 비례 | 실패한 프로젝트의 투자금이 남는 것 |

**타임아웃 실패를 투자자를 포함해 누구나 트리거할 수 있게 한 것이 핵심이다.** admin만 실패를 선언할 수
있으면 admin이 사라진 프로젝트의 투자금은 회수 경로가 없다. 단 완주한 프로젝트에는 적용되지 않는다
(`currentMilestone <= milestoneCount` 요구).

환불은 `refundAmount = invested × remaining / totalLocked`. 이미 집행된 몫은 빠진 채로 남은 잔액을
지분대로 나눈다.

**타임아웃 상수가 컨트랙트와 서버 양쪽에 있다는 게 이 설계의 약점이다.** `lib/onchain.ts`의
`MILESTONE_TIMEOUT_DAYS = 180`이 DB `deadlineAt` 계산의 단일 출처이고, 컨트랙트를 바꾸면 여기도 같이
바꿔야 한다고 주석에 못박았다. 코드가 강제하지 못하고 주석에 의존하는 자리다(§10.3).

### 2.7 감사 로그 — 기록에 없으면 일어나지 않은 일

청약·검증·집행·정산·권한 변경이 `AuditLog`에 남는다. 설계 결정 둘이 서로 반대다.

**① 감사 기록 실패가 본 작업을 깨뜨리지 않는다.** 로그 쓰기에서 난 예외가 트랜치 집행을 롤백시키면
안 된다 — 기록보다 거래가 우선이다.

**② 단, 트랜잭션 안에서 남길 때는 예외를 삼키지 않는다.** 트랜잭션 클라이언트를 받는 경로에서 예외를
삼키면 롤백 상태가 꼬인다.

같은 함수가 두 모드를 처리하되 예외 정책이 정반대다. 헷갈리기 쉬운 자리라 `lib/audit.ts` 한 곳에 몰아뒀다.

감사 항목 목록이 곧 화면 필터의 선택지다. **기록에 없으면 조회할 수도 없다.** admin이 모든 역할을
통과하는 대가로(§7.2) admin의 모든 동작이 여기 남는다.

### 2.8 검토했지만 쓰지 않은 것

**다중서명(multisig)으로 집행 승인.** 서명자 N명 중 M명이 동의해야 자금이 나가는 구조를 검토했다.
쓰지 않은 이유는 그게 **조건을 판정하지 않기 때문이다.** 서명자가 증빙을 봤는지 안 봤는지 코드가 알
방법이 없어, ①(사람 판정)으로 되돌아간다. 서명자 다수가 한 조직이면 도장이 여러 개가 될 뿐이다.

**외부 오라클로 증빙 판정.** 판정을 제3자 오라클에 맡기는 안. 이 제품이 판정해야 하는 것이 사진·영수증
같은 비정형 증거라, 오라클이 하는 일이 결국 우리가 하는 일과 같아진다. 신뢰 대상이 우리에서 오라클로
옮겨갈 뿐이고 그 오라클을 검증할 방법이 또 필요해진다.

**집행 조건을 온체인에만 두기.** 서버 게이트를 없애고 컨트랙트만 남기는 안. AI 판정 결과를 온체인에
올리려면 결국 서버 지갑이 `verifyMilestone`을 부르므로, 그 호출 직전의 조건 확인은 어차피 서버에서
한다. 서버 게이트를 지우면 그 확인이 라우트 핸들러 안으로 흩어질 뿐이라 유지했다.

## 3. AI에게 무엇을 맡기지 않았나

AI가 두 자리에 있고, 둘 다 최종 판단자가 아니다.

### 3.1 왜 LLM이 값을 내면 안 되나

운영 조언 계층에서 LLM에게 숫자를 직접 내게 하는 안이 가장 간단하다. 쓰지 않은 이유는 둘이다 —
**그 숫자가 어디서 왔는지 아무도 답할 수 없고, 같은 입력에 같은 값이 나오지 않는다.** 운영 판단과
정산에 그런 숫자를 쓸 수 없다.

그래서 `lib/llm-harness.ts`는 Tool-use ReAct 오케스트레이터다. **LLM이 정하는 것은 "어느 알고리즘을
부를까"까지고, 계산은 결정론적 함수가 한다.**

| LLM이 고를 수 있는 도구 | 실제 계산 |
|:---|:---|
| `maintenanceRisk` | 센서 드리프트 기반 예지보전 |
| `dliSchedule` | 요금·탄소집약도 연동 광주기 스케줄 |
| `cusumDrift` | MAD-CUSUM 관리도 |
| `holtWintersForecast` | 수요 예측 |
| `seedingPlan` | 파종량 계획 |
| `analyzeGrowthRecipe` | 생육 레시피 |

API 키가 없으면 규칙 기반 목업이 같은 인터페이스로 답한다. SDK 의존 없이 fetch REST만 쓴다.

**이 경계가 §2.3의 경계와 같은 모양이다.** 거기서는 "우리가 못 고치는 곳에 마지막 방어선"이었고,
여기서는 "재현되지 않는 것에 판정을 맡기지 않는다"다. 둘 다 **신뢰할 수 없는 주체를 경로에서 빼는 것**이다.

### 3.2 증빙 검증 — AI 판정이 곧 집행이 아니다

`lib/ai-vision.ts`가 이미지 + 프롬프트를 받아 JSON을 뽑는다. 키가 설정된 provider만
**Gemini → OpenAI → Anthropic** 순으로 시도한다. 라우트 코드를 고치지 않고 키만 채우면 폴백 체인에
합류한다. 현재는 무료 Gemini(`gemini-2.5-flash`)만 쓴다.

**자동 검증 실패는 자동 반려가 아니라 `manual_review` 큐로 간다**(§2.4). 판정 근거(신호별 초안·추출값·
교차대조 결과·신뢰도)는 조회할 수 있고, 운영자는 이의제기할 수 있다.

### 3.3 캐시가 판정 우회가 되는 경로

비용 절감을 위해 판정 결과를 캐시한다. 여기에 함정이 하나 있다.

```
cacheKey = `${signalType}:${sha256(imageBase64).slice(0, 16)}`
```

**캐시 키에 이미지 지문이 들어가야 한다.** 마일스톤 ID만으로 키를 만들면 같은 마일스톤에 아무 이미지나
올려도 이전 통과 결과가 재사용된다 — 그 자체가 위조 통과 경로가 된다. **캐시는 비용 절감 장치이지
판정 우회 장치가 아니다.**

이 함정은 일반화된다. **성능 최적화가 판정 경로에 놓이면 그 최적화가 곧 우회로가 된다.** 게이트 앞에
캐시·조기반환·단축평가를 넣을 때마다 같은 질문을 해야 한다.

## 4. 누구인지 어떻게 아나

### 4.1 이름·전화번호로는 성립하지 않는다

증권을 파는 이상 "누가 샀는지"를 확실히 알아야 한다. 자체 입력 폼으로는 본인확인이 되지 않고, 그 위에
쌓는 적격 판정·연간한도·양도제한이 전부 근거를 잃는다. **국가 발행 모바일 신분증에서 검증된 클레임을
받는다.**

경로 둘을 두고 같은 인터페이스로 감쌌다.

| 경로 | 무엇 | 상태 |
|:---|:---|:---|
| OACX (라온시큐어 OmniOne CX) | 정부 모바일 운전면허증 제출·파싱. `mobileid://` | **현재 프로덕션** |
| OpenDID Verifier (KOMSCO K-DID / OmniOne) | 자체 호스팅 Verifier에 VP 제출·검증. `omnione://` | 자체 구축 |

```ts
createOffer(policy: { claims: string[] })  →  { txId, qrData, deeplink }
getStatus(txId)                            →  pending | submitted | verified | failed
getClaims(txId)                            →  IdentityClaims | null
```

`IDENTITY_PROVIDER` 환경변수가 구현체를 고른다. 개발·시연용 `StubVerifier`는 3초 뒤 자동으로
`pending → verified`가 된다. **어느 구현이든 도메인 코드는 같은 세 메서드만 부른다** — 신분증 사업자가
바뀌어도 적격 판정 로직이 흔들리지 않게 하려는 것이다.

**OACX 호출 네 단계를 전부 서버에서 하는 것은 편의 문제가 아니라 이 연동의 핵심 제약이다.**

```
① POST /oacx/api/v1.0/trans              거래 토큰 발급 (JWT 유효 5분)
② POST .../authen/{qr|app}/request       QR base64 또는 딥링크 발급
③ POST .../authen/{qr|app}/result        사용자 제출 완료 후 검증 요청
④ GET  .../trans/{token}                 토큰 파싱 — 여기서만 개인정보가 나온다
```

파싱 API에 별도 인증이 없어, ④의 결과 토큰이 브라우저에 노출되면 그 토큰으로 누구나 개인정보를 파싱할
수 있다. 그래서 토큰이 클라이언트에 닿는 경로를 만들지 않았다.

OACX 서버는 **국내 IP만 받는다.** Vercel 함수 리전을 서울(`icn1`)로 고정한 이유이고, 국외 리전에서는
에러가 아니라 조용히 타임아웃한다. 실측과 되돌리기는 `../ops/oacx-status.md`에 있다.

### 4.2 받을 수 있어도 필요 없으면 받지 않는다

신분증 연동은 요청하면 많이 준다. **받은 값은 전부 유출 대상이 되므로, 판정에 필요한 최소로 줄인다.**

**영지식 모드.** `zkpType`을 주면 원본 값 대신 판정만 받는다.

| `zkpType` | 받는 것 | 안 받는 것 |
|:---|:---|:---|
| `AdultVerify` | 성인 여부 `true/false` | 생년월일 |
| `GenderVerify` | 성별 판정 | 주민번호·생년월일 |

투자 적격 판정에 필요한 것은 "만 18세 이상인가"뿐이고 생년월일 자체가 아니다. 신분증 연동에서 영지식을
쓸 수 있는 자리가 정확히 여기다.

**CI를 원문으로 저장하지 않는다.** CI(연계정보)는 전 서비스 공통 식별자라 원문을 보관하면 유출 시 타
서비스 계정까지 연결된다. 중복가입 판별에는 **동일성만** 필요하다.

```
hashCi(ci) = sha256(`${IDENTITY_CI_SALT}:${ci}`)
```

`IDENTITY_CI_SALT`가 없으면 던진다 — 시크릿 없는 해시는 무지개표 한 번에 뚫린다. 생년월일도 같은 이유로
저장하지 않고 `ageFromBirth()`로 만 나이를 계산해 성인 여부만 남긴다.

**"없으면 던진다"가 이 코드베이스의 반복 패턴이다.** `JWT_SECRET`, `IDENTITY_CI_SALT`,
`CUSTODY_MASTER_KEY` 셋 다 미설정 시 기본값으로 물러서지 않고 예외를 던진다. 빈 시크릿으로 서명하거나
평문으로 저장하는 경로는 있으면 언젠가 밟힌다.

### 4.3 신원을 체인에 묶는 이유

검증을 통과하면 서버가 `FarmToken.registerIdentity(wallet, didHash)`를 호출해 지갑과 DID 해시를
온체인에 바인딩한다. 이게 양도제한이 성립하는 근거다.

```solidity
function _update(address from, address to, uint256 value) internal override {
    if (from != address(0) && to != address(0)) {
        require(isVerified(from) && isVerified(to), "FarmToken: holder not verified");
    }
    ...
}
```

2차 이전(P2P)은 송·수신 지갑이 **모두** 신원 등록돼 있어야 한다. `from == address(0)`인 발행은 예외다 —
청약 발행을 신원 게이트 밖에 둬야 신원 등록 전에도 구좌가 나간다.

**1지갑 = 1신원, 1신원 = 1지갑**(§1.3의 부정 ⑤). `identity[wallet] → didHash`와
`didToWallet[didHash] → wallet` 양방향 매핑을 둬, 한 사람이 지갑을 여러 개 만들어 양도제한을 우회하는
것을 막는다. 재바인딩은 `revokeIdentity` 후 재등록만 가능하다.

**대가가 남는다.** `identity` 매핑이 public이라 "지갑↔DID 해시" 연결이 온체인에 노출된다. 해시라 원문은
아니지만 링크빌리티는 남는다(§10.1 ⑤). 온체인 검증 가능성과 프라이버시를 맞바꾼 자리다.

### 4.4 투자자는 개인키를 다루지 않는다

투자자에게 지갑 관리를 시키면 이 제품의 사용자 대부분이 진입하지 못한다. 서버가 1인 1지갑
(`CustodyWallet.userId` unique)을 만들어 보관한다.

개인키는 **AES-256-GCM**으로 암호화하고 **DB에는 `keyRef` 하나만** 든다. 그 값만으로는 키를 복원할 수
없고 마스터 키(`CUSTODY_MASTER_KEY`, 32바이트 hex)가 따로 있어야 한다. 마스터 키가 없으면 지갑을
만들지 않는다. 지갑 주소는 admin 응답에만 싣고 투자자 화면에는 내보내지 않는다.

**보유 구좌 발행·이전은 전부 운영키 트랜잭션이고, 투자자 개인키 서명은 발생하지 않는다.** 수탁을
택한 이상 "투자자가 스스로 서명했다"는 성질은 포기한 것이다. 신원 확인(외부 기관)과 체인 서명(운영지갑)이
왜 다른 주체인지는 `identity-and-signing.md`가 다룬다.

OpenDID의 Wallet SDK와는 다른 층이다. 그쪽은 신원·VC 보관용이고 이쪽은 증권 보유용이다.

## 5. 돈이 어디서 나와 어디로 가나

### 5.1 왜 운영자 매출에서 떼지 않나

투자자 회수금 재원으로 가장 자연스러운 후보는 운영자 매출이다. 쓰지 않았다.

**매출 연동이면 운영자가 들어오지 않는다.** 매출의 일정 비율을 떼는 구조는 장사가 잘 될수록 부담이
커진다. 이 제품이 유치해야 하는 대상은 자본이 없어 창업을 못 하던 사람이고, 그들에게 성공의 대가로
지분을 요구하면 남는 선택지가 기존 대출과 다르지 않다.

그래서 **운영자는 매출 100%를 소유하고 이용료를 지불한다.** 회수금은 FarmFi 플랫폼 수수료 풀에서 나온다.

| 수수료 원천 | 처리 |
|:---|:---|
| 플랫폼 이용료 (월/사이트) | 풀에 포함 |
| 체험프로그램 중개 수수료 | 풀에 포함 |
| B2B 신규계약 성사 수수료 | 풀에 포함 (FarmFi가 성사시킨 증분 매출에만) |
| 온보딩피 (1회성/사이트) | **풀에서 제외** — 라운드 셋업 대가로 본체 귀속 |

풀의 60%가 분기 변동 회수금, 40%가 FarmFi 운영이다. `lib/waterfall.ts`가 이 산식의 정본이고, 기획안의
어느 절을 따랐는지까지 코드 주석에 남겼다.

**이 산식이 흔들리면 제품의 전제가 흔들린다.** 운영자 주머니를 건드리지 않는 구조가 전제인데, 재원이
모자라 매출 연동으로 되돌아가면 §5.1 전체가 무너진다. 지금 이 산식은 검증된 것이 아니라 가정이다(§10.3).

지급 사무(`lib/payout.ts`)는 산출과 분리한다. 지급 예정 건을 등록하고 상태(예정/완료/실패)와 증빙만
관리하며, 실제 계좌이체는 하지 않는다.

### 5.2 청약 상태 기계 — 전제를 하나씩 건다

```
DRAFT → IDENTITY_REQUIRED → ELIGIBILITY_CHECKED → CONSENT_REQUIRED
      → AWAITING_DEPOSIT → DEPOSIT_CONFIRMED → COMPLETED
                         ↘ DEPOSIT_FAILED
                         ↘ CANCELLED
```

**각 전이에 전제가 하나씩 붙는다** — 신원 검증 없이 적격 판정으로 못 가고, 동의 없이 가상계좌를 받지
못하고, 입금 확인 없이 청약이 확정되지 않는다. 화면 I-02(적합성) → I-03(최종확인·서명·납입) →
I-04(완료)가 이 순서를 그대로 민다.

적격 판정은 `lib/identity/investor-limit.ts`가 한다.

| 요건 | 규칙 |
|:---|:---|
| 실명 | `realName` 필수. 없으면 부적격 |
| 연령 | `adult === true` 또는 계산 나이 ≥ 18. 미달·불명이면 부적격 |
| 한도 | 통과 시 일반투자자 연간 한도 부여 |

판정 결과에 `reasons` 배열이 함께 나온다 — 화면이 "왜 안 되는지"를 그대로 보여주기 위해서다.
**한도 수치는 확정값이 아니다.** 자본시장법과 온라인소액투자중개 시행령을 따라야 하고, 실 서비스 전
법무 검토 후 상수를 확정한다. 코드에 그렇게 표시해 뒀다(§10.2).

### 5.3 동의 문서를 고쳐 쓰지 않는 이유

**본문을 바꾸려면 `version`을 올려 새 행을 만든다.** 옛 행은 `isActive = false`로 두되 지우지 않는다.
이미 동의한 사람이 본 문장이 나중에 바뀌면 **"무엇에 동의했는지"를 증명할 수 없다.**

동의 기록(`AgreementConsent`)에는 **문서 해시를 복사해 둔다.** 문서 행을 잘못 건드려도 동의 시점의
본문이 무엇이었는지 남는다. 동의 시각·전자서명값·본인확인 세션을 함께 저장한다.

필수 문서를 모두 동의해야 `POST /api/investments/[id]/consent`가 통과하고, 그때 동의한 문서들을 묶은
해시를 `Investment.agreementHash`에 남긴다 — 체인에 올릴 계약 해시다.

### 5.4 입금 — 웹훅은 몇 번이든 온다

동의를 마치면 건별 가상계좌를 발급하고 `AWAITING_DEPOSIT` + 입금기한을 건다. 은행 입금이 확인돼야
청약이 반영된다.

**멱등성은 `DepositEvent.providerTransactionId` unique로 잡는다.** 같은 거래번호는 웹훅이 몇 번 와도
한 번만 처리된다. 웹훅 서명은 HMAC + `timingSafeEqual`로 검증한다 — 일반 문자열 비교는 타이밍 공격에
노출된다.

실패 분기 넷을 화면에서 구분한다. **하나로 묶으면 사용자가 무엇을 해야 하는지 알 수 없다.**

| 분기 | 처리 |
|:---|:---|
| 발급 실패 | 재시도 안내 |
| 입금기한 만료 | `DEPOSIT_FAILED`로 닫고 재신청 경로 |
| 금액 불일치 | `AMOUNT_MISMATCH` → 관리자 큐 |
| 확인 지연 | `POST .../deposit-inquiry`로 조회 요청 |

### 5.5 발행 — DB와 체인을 한 트랜잭션에 묶을 수 없다

입금이 확인되면 보유 구좌를 발행해야 하는데, DB 커밋과 체인 전송은 원자적으로 묶이지 않는다. 순진하게
짜면 둘 중 하나가 실패했을 때 상태가 갈린다.

**트랜잭셔널 아웃박스로 푼다.** "발행하기로 했다"는 사실을 먼저 커밋하고, 전송은 재시도로 따라붙게 한다.

```
은행 입금 확인 ──같은 트랜잭션── HoldingIssuance(PENDING) 기록
                                       │
                             Chain Relay가 그 행을 집어 mint 전송
                                       │
                                SENT(해시) → CONFIRMED
```

`eventId = deposit:<거래번호>:mint`가 unique다. 웹훅이 몇 번 오든 발행 행은 하나이고, 중간에 프로세스가
죽어도 PENDING 행이 남아 이어서 처리된다. **잡 큐를 따로 두지 않았다 — 발행 행이 곧 큐다.**

실패는 지수 백오프 5회(30초·1분·2분·4분·8분) 후 `CHAIN_FAILED` + 운영 알림.

**체인이 실패해도 입금과 청약은 되돌리지 않는다.** 돈은 이미 들어왔고, **체인 기록은 그 사실의 사본이지
원본이 아니다.** 반대로 청약이 `DEPOSIT_FAILED`로 끝난 건은 발행을 `CANCELLED`로 닫는다 — 환불 대상에
구좌를 발행하지 않는다.

**배당은 스냅샷 기준으로 낸다**(§1.3의 부정 ⑥). 회차마다 `snapshotBlock = block.number`를 기록하고
청구 시 그 블록 시점의 잔고로 계산한다.

```solidity
uint256 balance = farmToken.balanceOfAt(msg.sender, rounds[round].snapshotBlock);
uint256 amount = balance * rounds[round].perToken;
```

스냅샷이 없으면 발표 → 매수 → 청구 → 매도로 무위험 차익을 낼 수 있고 기존 보유자의 몫이 희석된다.
`FarmToken`이 `Checkpoints.Trace208`로 모든 mint/burn/transfer 후 잔고를 기록하는 이유가 이것이다.

`FarmToken.decimals()`가 **0**인 것도 같은 계열의 결정이다. 1구좌 = 정수 1. 증권 지분에 소수점이 없어야
하고, 이 결정 덕분에 명세의 `HoldingLedger`를 새로 배포하지 않고 `FarmToken.mint`가 그 역할을 한다.

### 5.6 불일치를 자동으로 고치지 않는 이유

`lib/reconciliation.ts`가 DB의 보유 구좌와 체인 잔액을 맞춰본다.

**① 영수증 재조회.** 전송은 했는데(SENT + 해시) 결과를 못 받은 건을 체인에 다시 묻는다. Relay는 "해시가
있으면 성공"으로 넘기지만 여기서는 영수증을 실제로 확인해 **되돌려진 트랜잭션을 잡는다.** revert면 해시를
지운다 — 지우지 않으면 Relay가 실패를 성공으로 오인한다.

**② 건수 대조.** 지갑별 DB 확정 구좌 합과 `balanceOf`를 비교한다.

**불일치는 자동으로 고치지 않는다.** 어느 쪽이 맞는지 기계가 판단할 수 없고, 잘못 맞추면 구좌가 이중으로
생기거나 사라진다. `ReconciliationEntry`(OPEN·RESOLVED)에 적어 사람에게 넘기고, 해소에는 사유를 필수로
받는다. §2.4의 `manual_review`와 같은 판단이다.

스케줄은 `/api/cron/reconcile`(`CRON_SECRET` 필요) — 영수증 10분 주기, 전체 대사 하루 한 번.

### 5.7 왜 "에스크로"라고 부르지 않나

투자금은 팜피 고유계정과 분리해 **신탁**으로 보관한다. 인가·계약 사항이라 출시 전 게이트에서 확정되고,
그때까지는 `FundCustodyAdapter` 뒤의 Mock이다.

**용어를 섞으면 책임 주체가 흐려진다.** 도산 격리는 신탁의 역할이고, 조건 충족 시 집행은 마일스톤
게이트의 역할이다. 둘 다 에스크로가 아니다. 온체인 `Escrow.sol`은 **집행 게이트를 가리키는 이름이지
보관 주체가 아니다.**

**화면에 지금 어느 단계인지 그대로 적는다** — "분리보관 · 출시 시 신탁 적용". Mock을 실물처럼 보이게
하면 데모는 매끄럽지만 그 화면이 그대로 거짓말이 된다. §9의 원칙 ④가 이것이다.

### 5.8 파일럿이 통과해야 나머지가 열린다

`RoundGate.sol`이 파일럿 1호점의 전 마일스톤 통과를 나머지 사이트 집행의 전제로 건다.

```solidity
function pilotCompleted() public view returns (bool) {
    return !p.projectFailed() && p.currentMilestone() > p.milestoneCount();
}
function isOpen(address site) external view returns (bool) {
    return site == pilot || pilotCompleted();
}
```

파일럿 자신은 항상 열려 있다. **청약(모집)은 게이트와 무관하게 진행되고**, 파일럿이 실패하면 나머지
사이트 투자금은 미집행 상태 그대로 환불 경로를 탄다. **검증 안 된 모델을 여러 매장으로 동시에 퍼뜨리지
않기 위한 장치**이고, `setPilot`도 1회만 가능하다.

## 6. 웹과 앱을 왜 한 서버에 뒀나

### 6.1 제약이 먼저였다

Next.js 하나가 화면과 API를 함께 낸다. 별도 API 서버가 없다.

**선택의 출발점은 팀 규모와 기간이다.** 서버를 나누면 CORS·인증 토큰 전달·배포 파이프라인 이중화가
따라오고, 그 작업은 이 제품의 주장(§0)과 아무 상관이 없다. 먼저 정해진 것은 이 제약이었고, 아래 셋은
그 선택이 실제로 도움이 된 지점이다 — 이 선택을 하게 만든 이유가 아니다.

**① 화면과 API가 같은 타입을 본다.** Prisma가 생성한 타입을 라우트와 화면 양쪽이 그대로 쓴다. 스키마를
고치면 `tsc --noEmit`이 두 쪽을 동시에 깨뜨려 어긋난 채로 배포될 길이 없다. **셋 중 이것만 매일 작동한다.**

**② 세션 검증이 한 곳이다.** 서버를 나누면 세션을 두 곳에서 검증하게 되고, 두 검증이 어긋나는 순간이
그대로 취약점이 된다. 다만 나눠도 잘 하면 되는 문제이므로, 이건 이득이지 근거는 아니다.

**③ 배포 단위가 하나다.** "프론트는 새 버전인데 API는 옛 버전"인 상태가 존재하지 않는다. 이것도 나눈
구조에서 관리 가능한 문제라 마찬가지다.

### 6.2 대가와 첫 분리선

| | 웹 (`frontend/`) | 앱 (`app/`) |
|:---|:---|:---|
| 누가 쓰나 | 투자자 · 건물주 · 구매자 · 관리자 | 운영자 |
| 무엇을 하나 | 청약 · 보유 조회 · 심사 · 정산 | 매장 운영 · 모니터링 · 픽업 · 증빙 |
| 스택 | Next.js 14 | Expo React Native |

**공유하는 것 셋** — 같은 서버, 같은 DB(`prisma/schema.prisma`), 같은 JWT. 접점(보증서 확인 · 설비 연결 ·
픽업 스캔 · 증빙 제출)은 `../spec/app-feature-spec.md` 0.2 표가 정본이다.

세션은 HS256 JWT 하나다. httpOnly 쿠키(`session`, 7일)에 담고, **쿠키를 쓸 수 없는 모바일 앱은 같은
토큰을 `Authorization: Bearer`로 보낸다.** 앱 전용 인증을 따로 만들면 권한 규칙이 두 벌이 된다.

대가는 분명하다.

- 웹 트래픽과 배치 작업이 같은 런타임을 공유한다
- **웹 배포가 앱에 영향을 준다** — 앱 담당이 배포 시점을 통제하지 못한다
- 스키마 변경은 양쪽 담당이 합의해야 한다. 그래서 스키마 변경은 화면 변경과 다른 커밋 단위로 다룬다

**첫 분리선은 도메인 로직(`lib/`)이다.** 그래서 `lib/`가 Next 런타임에 의존하지 않게 유지한다 —
`next/headers`·`NextRequest` 같은 것을 도메인 모듈이 부르지 않는다. 이 규칙을 지키는 한 `lib/`를
통째로 들어내 별도 서버로 옮길 수 있다. 팀이 커지면 여기가 첫 번째로 아플 자리다(§10.1 ⑦).

## 7. 층을 어디서 잘랐나

### 7.1 규칙을 라우트가 아니라 `lib/`에 두는 이유

라우트 핸들러의 책임을 넷으로 고정했다 — **권한 확인 · 입력 검증 · 도메인 함수 호출 · 직렬화.**

**규칙이 라우트 안에 들어가면 그 규칙은 그 HTTP 경로로만 부를 수 있다.** 배치나 앱에서 같은 규칙이
필요할 때 복사본이 생기고, 복사본 둘이 어긋나면 어느 쪽이 정본인지 코드가 말하지 못한다.
집행 게이트가 서버·온체인 두 겹인 것(§2.3)은 의도한 이중화지만, 게이트 로직이 라우트마다 흩어지는 것은
그냥 사고다.

같은 이유로 규칙을 한 파일씩에 몬다 — 게이트는 `milestone-gate.ts`, 체인 전송은 `chain-relay.ts`,
신원은 `auth.ts`, 좌표 변환은 `crop-normalize.ts`, 단가는 `optimization-params.ts`.

**`BigInt` 직렬화도 한 곳(`lib/serialize.ts`)이다.** 금액을 `bigint`로 다루므로 `JSON.stringify`가 그대로는
던진다. 라우트마다 변환하면 어떤 라우트는 문자열, 어떤 라우트는 숫자로 나가 화면이 두 형식을 모두
처리해야 한다.

### 7.2 권한 판정을 미들웨어에 두지 않는 이유

`middleware.ts`가 하는 일은 없어진 경로를 지금 경로로 보내는 것뿐이다(`/wallet` → `/verify/account`,
`/portfolio` → `/investor/holdings` 등). **권한은 보지 않는다.**

권한 판정을 미들웨어에 두면 라우트 핸들러가 "누가 여기 도달했는지" 모른 채 동작한다. 그리고 매칭 규칙
하나를 빠뜨리면 그 경로가 통째로 열린다 — **누락이 조용한 실패가 되는 구조**다. **판정은 그 판정을 쓰는
곳에서 한다.**

`requireRole(role)`은 미인증이면 401, 역할 불일치면 403을 **Response 객체로 던진다.** 라우트는 그대로
되던지면 된다.

| 역할 | 무엇을 하나 |
|:---|:---|
| `investor` | 청약 · 보유 조회 · 회수금 수령 |
| `operator` | 증빙 제출 · 집행 수령 · 매장 운영 |
| `landlord` | 공간 등록 · 계약 |
| `admin` | 심사 · 승인 · 발행 콘솔 · 대사 · 권한 |

**`admin`이 모든 역할을 통과한다.** 심사와 운영 지원이 전 역할의 화면을 봐야 하기 때문이고, 그 대가로
admin의 모든 동작이 §2.7의 감사 로그에 남는다. 권한을 넓히는 대신 기록으로 갚는 거래다.

**신원은 요청 본문에서 오지 않는다.** `userId`는 검증된 JWT의 `sub`에서만 읽는다. 클라이언트가 보낸 값을
신뢰하는 경로가 하나라도 있으면 나머지 방어가 전부 무의미해진다. 토큰이 만료·위조·손상되면 예외를 삼키고
미인증으로 처리한다 — 실패 사유를 응답에 흘리지 않는다.

### 7.3 계산 계층을 순수 함수로 두는 이유

학습·최적화 계층은 DB·네트워크에 의존하지 않는다. **API 라우트와 모바일 앱이 같은 함수를 공유하기
위해서다.** 파이프라인 조립도 한 곳(`optimization-report.ts`)에서 한다 — 웹 페이지와 API가 각자 계산하면
입력이 조금씩 갈라져 **같은 프로젝트인데 다른 숫자가 나온다.**

계층 경계는 셋이다.

| 계층 | 질문 | 근거 문서 |
|:---|:---|:---|
| 생육 레시피 | 환경 목표를 **무엇으로** 정하나 | `growth-recipe-rationale.md` |
| 운영최적화 | 그 목표를 **어떻게 싸게** 달성하나 | `optimization-rationale.md` |
| 자동제어 | 그 목표에 **실제로 도달**시키나 | `optimization-rationale.md` (제어·HIL 절) |

**두 층이 목적함수를 공유해야 한다.** 레시피가 수율만 최대화하면 비싼 목표를 정하고 스케줄 층이 그 비싼
목표를 싸게 달성하는 구조로 수렴한다 — 맞물린다는 말이 실제로는 성립하지 않는다. 그래서 레시피 층의
목적함수를 수익(매출 − 운전비)으로 두어 두 층이 같은 것을 최대화하게 한다. **계산 선택이 아니라 층
경계를 정하는 결정이라 여기에 적는다.**

완성 시의 닫힌 루프는 이렇다.

```
IoT 관측 → 학습 → 레시피·스케줄 산출 → 운영자가 적용 → 다음 사이클 수확 → 다시 학습
```

적용은 운영자가 누를 때만 하고, **산출값과 실제 적용값을 함께 남긴다.** 정산과 판정에는 적용값을 쓴다.
둘을 구분해 기록하지 않으면 "권고대로 했는데 결과가 나빴다"와 "권고를 안 따랐다"를 사후에 가를 수 없다.

### 7.4 무엇을 어댑터 뒤에 두었나

우리가 만들지 않은 것은 전부 인터페이스로 감쌌다 — 은행·PG(`lib/payment.ts`), 신탁
(`lib/fund-custody.ts`), 신분증(`IdentityVerifier`), 공개데이터(`lib/opendata.ts`).

**이유는 교체 가능성이 아니라 검증 가능성이다.** 실 사업자 계약은 출시 전 게이트라 지금 붙일 수 없다.
어댑터가 없으면 그때까지 흐름 전체를 한 번도 돌려볼 수 없다. Mock을 물려 두면 **집행 게이트·상태 기계·
멱등성 같은 우리 몫의 로직을 지금 검증할 수 있다.**

대가는 §10.1 ②다. Mock으로 흐름이 도는 것과 실 API에서 도는 것은 다르고, 지금 확인할 수 있는 최대치는
전자까지다.

**어댑터 뒤에 두지 않은 것도 있다.** 체인 호출(`lib/onchain.ts`)은 viem에 직접 붙어 있다. 체인은 교체
대상이 아니라 환경변수로 지정하는 대상이라(`ONCHAIN_CHAIN_ID`·`ONCHAIN_RPC_URL`), 미설정이면 Polygon
Amoy로 폴백한다. 주소나 키가 없으면 `isOnchainEnabled()`가 false를 반환하고 체인 호출이 `null`을 낸다 —
**배포 전에도 나머지 흐름이 그대로 돈다.**

### 7.5 데이터 계층에서 한 결정 둘

PostgreSQL(Supabase) 하나에 모델 47개. **스키마가 웹·앱의 계약이다.**

**연결 경로가 둘이고 섞으면 마이그레이션이 조용히 실패한다.**

| 작업 | 포트 | 이유 |
|:---|:---|:---|
| 시드 · 일반 쿼리 (DML) | 6543 (트랜잭션 pooler) | 서버리스에서 연결을 아낀다 |
| `db push` (DDL) | 5432 (세션 pooler) | 트랜잭션 pooler는 DDL을 넘기지 못한다 |

DDL은 `--url`로 5432를 덮어써야 한다. Prisma 7은 driver adapter를 요구해 `new PrismaClient()` 무인자가
동작하지 않고 `PrismaPg`를 주입해야 하며, datasource URL은 스키마가 아니라 `prisma.config.ts`에 있다.

**기간 조회는 `lib/data-window.ts`를 거친다.** 시드는 실행 시점 기준 상대 날짜로 데이터를 넣는데 조회는
현재 시각에서 역산한 창을 쓴다. 시드 후 창 길이보다 오래 지나면 두 구간이 겹치지 않아 결과가 0건이 되고,
API는 200을 반환하는데 화면만 비어 **데이터가 없는 건지 기능이 없는 건지 구분되지 않는다.** 최신 레코드를
창의 끝점으로 삼고 화면에 "데이터 기준일"을 표기한다. §9의 원칙 ①이 데이터 계층에 나타난 형태다.

## 8. 검증 — 이 구조가 맞는지 어떻게 아나

| 대상 | 방법 |
|:---|:---|
| 타입 | `npx tsc --noEmit` |
| 도메인 로직 | `npm test` — `tsx --test "src/**/*.test.ts"` |
| 컨트랙트 | `forge test` |
| 렌더 | `npm run dev` → 라우트별로 `design/screens/`의 좌표·색·폰트 덤프와 대조 |
| 프로덕션 빌드 | Vercel 프리뷰 배포 |

**컨트랙트는 불변식 테스트가 중요하다.** 개별 함수가 전부 통과해도 **호출 순서 조합에서 잔액이 어긋나는**
경우를 단위 테스트로는 못 잡는다. `Escrow.invariant.t.sol`이 `totalLocked = totalReleased + remaining`을
고정한다.

| 파일 | 무엇 |
|:---|:---|
| `Escrow.t.sol` | 청약 · 검증 · 집행 · 실패 · 환불 |
| `Escrow.invariant.t.sol` | 불변식 |
| `FarmToken.t.sol` | 발행 상한 · 화이트리스트 · 신원 바인딩 · 체크포인트 |
| `Dividend.t.sol` | 스냅샷 기준 분배 · 중복 청구 차단 |
| `V16Hardening.t.sol` | 하드닝 회귀 — 타임아웃 · 라운드게이트 · 게이트 설정 시점 |

**학습 계층은 반대 방향 데이터를 넣어 확인한다.** `lib/` 테스트 7묶음이 주장마다 값이 실제로 움직이는지
본다 — "잡음이 5배인데 불확실성이 안 커졌다", "공짜인데 DLI가 움직였다" 같은 실패 메시지가 그 설계다.
값이 그럴듯하게 나오는 것과 옳은 방향으로 반응하는 것은 다르다.

인수 기준은 `../spec/feature-spec.md` 18장의 역할별 테스트를 쓴다 — 중복 은행 웹훅이 와도 투자금 1회 반영,
같은 `eventId`로 재시도해도 보유 구좌 이중 발행 없음, 승인되지 않은 마일스톤은 집행 API가 거부.

**저장소 경로에 한글을 넣지 않는다.** 한글이 섞이면 `next build`가 readlink EISDIR로 죽는다. 빠른 검증은
`tsc --noEmit` + `next dev`로 하고, 프로덕션 빌드는 Vercel(Linux)에서 확인한다.

`DEMO_MODE=cached`를 두면 AI 호출 대신 `DemoCache`의 저장된 결과를 쓴다. 발표장 네트워크가 불안정하거나
외부 API가 흔들려도 시연이 멈추지 않게 하는 장치다.

## 9. 이 구조를 지탱하는 원칙 여섯

**① 판정할 수 없으면 판정하지 않는다.** 센서 결측은 반려가 아니라 `manual_review`, 대사 불일치는 자동
수정이 아니라 사람에게, 표본이 모자란 설명력은 0이 아니라 `null`, 외기 데이터가 없으면 그 분석은
`unavailable`이다. **판정하지 않은 것이 "정상"으로 보이는 경로**가 가장 위험하다.

**② 규칙은 한 곳에만 둔다.** 두 벌이 되는 순간 어느 쪽이 정본인지 코드가 말하지 못한다. 이중화는
의도한 곳(§2.3)에만 둔다.

**③ 우리가 못 고치는 곳에 마지막 방어선을 둔다.** 서버 게이트는 우리가 고칠 수 있고 컨트랙트는 못 고친다.
투자자가 우리를 믿지 않아도 성립하는 층이 하나는 있어야 한다.

**④ 없는 값을 지어내지 않는다.** Mock을 실물처럼 그리지 않고 화면에 단계를 적는다. 근거 없는 비용 항은
0으로 두고 표에 밝힌다. 내부값에서 상수를 빼 외기온도를 만들어 넣지 않는다.

**⑤ 받을 수 있어도 필요 없으면 받지 않는다.** 보관하지 않은 값은 유출되지 않는다.

**⑥ 갇히는 상태를 만들지 않는다.** 관문을 세게 걸수록 탈출구가 필요하다 — 타임아웃 실패는 누구나
트리거하고, 이의제기 경로가 있고, 환불은 지분대로 자동 계산된다.

## 10. 가정과 한계

### 10.1 원리적 한계 — 구현을 더 해도 없어지지 않는 것

**① 학습 스택은 실 수확 라벨이 0건이다.** 검증된 것은 "정답을 아는 합성 반응면에서 그 정답을 되찾는다"
이지 "실제 재배에서 맞는 목표를 낸다"가 아니다. 매장이 돌고 사이클이 쌓이기 전에는 이 간극이 좁혀지지
않는다. 상세는 `growth-recipe-rationale.md` §10.1.

**② Mock으로 흐름이 도는 것까지가 지금 확인할 수 있는 최대치다.** 은행·PG·신탁 실 API는 계약과 인가
사항이라 개발로 앞당길 수 없다. 어댑터 경계가 맞는지는 실 연동 때 처음 검증된다.

**③ 증빙 위조를 완전히는 막지 못한다.** §2.5의 교차검증은 "영수증과 무관한 사진"을 잡지만, 실제로 설비를
사서 찍고 되판 경우는 잡지 못한다. 사진·영수증 기반 판정의 상한이고, IoT 신호가 이를 부분적으로 보완하되
설비가 실제로 그 매장에 있는지까지는 증명하지 않는다.

**④ 온체인 방어선은 우리가 배포한 컨트랙트를 신뢰하는 것까지다.** 배포 후 못 고친다는 성질은 배포된
바이트코드가 감사받았을 때만 의미가 있다. 지금은 자체 테스트(§8)까지이고 외부 감사는 받지 않았다.

**⑤ 온체인 신원 링크빌리티가 남는다.** `FarmToken.identity` 매핑이 public이라 지갑↔DID 해시 연결이
노출된다(§4.3). 검증 가능성과 맞바꾼 것이라 구조를 바꾸지 않으면 없어지지 않는다.

**⑥ 수탁 구조에서 투자자는 자기 자산을 직접 통제하지 않는다.** 마스터 키를 가진 쪽이 모든 투자자 지갑에
접근할 수 있다. KMS/HSM으로 옮겨도 성질은 같고, 운영 주체 신뢰를 없애지는 못한다.

**⑦ 웹과 앱이 같은 서버·같은 DB를 쓴다.** 웹 배포가 앱에 영향을 주고 스키마 변경은 양쪽 합의가 필요하다.
결함이 아니라 선택이지만(§6), 팀이 커지면 첫 번째로 아플 자리다.

### 10.2 데이터와 계약이 있어야 닫히는 것

계획한 개발은 끝났다. 화면 62개와 그 화면이 도는 API, 투자금 납입 실계, 체인 기록·보유 구좌 발행과 대사,
동의 문서, 검증 근거 조회와 심사 큐, 운영자 보증서, 정산 확정과 지급 실패 처리, 픽업 바코드, 레시피 적용
경로가 모두 동작한다. 집행 게이트는 서버·온체인 양쪽에서 돌고, 모바일 신분증 인증은 프로덕션에 배포돼
실 Verifier와 연동된다.

남은 것은 구현을 더 해서가 아니라 **실 데이터와 실 계약이 있어야 닫히는 두 자리**다.

| 무엇 | 지금 생기는 일 |
|:---|:---|
| 레시피 관측이 합성이다 | `setpoints` 라우트가 `generateObservations`로 관측을 만든다. 실 수확 라벨이 들어오는 경로가 없어 §7.3의 루프가 열려 있다 |
| 프로젝트 소유자 모델이 없다 | `Project`에 소유자 필드가 없어 "내 프로젝트만"을 강제할 수 없다. §2.5의 검증 라우트를 admin 전용으로 둘 수밖에 없다 |

**모바일 신분증은 테스트 환경이다.** OACX는 발급기관이 내준 테스트 환경이고, 자체 호스팅 Verifier는 홀더 지갑앱이
없어 실 QR이 자동으로 verified가 되지 않는다. 시연용 경로를 admin 게이트 뒤에 둔다.

**투자 모집 기능은 법률 검토 전이다.** 실제 활성화는 금융 파트너 승인까지 feature flag로 막는다.
투자자 연간한도 수치도 법무 검토 후 확정한다.

### 10.3 근거가 약한 결정

여기 있는 것들은 지금 상태로 발표하거나 인용하면 반박당할 수 있는 자리다.

**① 워터폴 60:40과 수수료 원천 구성.** 풀의 60%를 회수금으로 돌린다는 비율은 기획안에서 온 것이고
실측이나 시뮬레이션으로 검증되지 않았다. 운영자가 실제로 낼 이용료 수준, 체험프로그램 중개 건수,
B2B 성사율이 전부 가정이다. **이 산식이 회수 가능성의 근거인데, 그 근거가 아직 데이터가 아니다**(§5.1).

**② 마일스톤 타임아웃 180일.** 컨트랙트와 서버 양쪽에 같은 상수가 있고 동기화를 주석이 강제한다.
코드가 강제하지 못하는 자리라, 컨트랙트를 재배포할 때 서버 상수를 놓치면 DB `deadlineAt`과 온체인
마감이 갈린다. 180이라는 값 자체도 공사·인허가 기간에서 역산한 것이 아니라 여유값이다.

**③ 교차검증 카테고리 4종.** 조명·센서·재배설비·관수로 나눈 것은 스마트팜 설비 구성에서 온 것이지
오분류율을 측정해 정한 것이 아니다. 카테고리를 넓게 잡으면 무관한 항목이 같은 카테고리로 묶여 통과하고,
좁게 잡으면 정상 증빙이 `manual_review`로 떨어진다. 어느 쪽으로 틀렸는지 알 데이터가 없다.

**④ `admin`이 모든 역할을 통과하는 것.** 감사 로그로 갚는다고 썼지만, 로그는 사후 추적이지 사전 차단이
아니다. 운영 지원 편의를 위해 권한 경계를 넓힌 결정이고, 프로젝트 소유자 모델이 들어오면 다시 좁혀야 한다.

**⑤ 웹과 앱의 팔레트가 이미 갈렸다.** 웹은 `surface #F1F4F2` · `danger #DC2626`을, 앱은
`surface #F2F2F0` · `danger #A34A3D`를 쓴다. 앱은 정상·주의·위험 3단계를 색으로 구분하고 웹은
Figma 최종본 색을 따른다. **같은 팔레트를 공유한다는 전제가 지금은 성립하지 않는다** — 어느 쪽을
정본으로 삼을지 정해야 한다.

**⑥ §6의 근거 ②·③.** 세션 검증과 배포 단위는 서버를 나눈 구조에서도 관리 가능한 문제다. 모놀리식을
정당화하는 논거로 쓰면 반박당한다. 실제로 매일 작동하는 이득은 ①(타입 공유) 하나다.

## 부록 B. 요청 하나가 지나가는 경로

§7의 층 구분이 실제 파일로는 이렇게 나타난다.

```
브라우저
  └ app/operator/milestones/page.tsx        ← 라우트. 7줄. metadata와 컴포넌트 호출뿐
      └ components/screens/operator/MilestonesScreen.tsx   ← "use client". 화면 전부
          └ components/screens/api.ts       ← useQuery + 응답 타입. 화면은 fetch를 직접 쓰지 않는다
              └ app/api/milestones/route.ts ← requireRole → 입력 검증 → 도메인 호출 → 직렬화
                  └ lib/milestone-gate.ts   ← 규칙
                      └ lib/db.ts → PostgreSQL
```

**`page.tsx`를 얇게 두는 이유.** 라우트 파일에 로직이 들어가면 그 화면은 그 URL에서만 쓸 수 있다.
화면을 컴포넌트로 두면 관리자 화면이 운영자 화면 일부를 그대로 품을 수 있고, Figma 화면 ID와 파일이
1:1로 대응해 대조가 기계적으로 된다. 화면 컴포넌트는 역할별 디렉터리 여섯으로 나눈다 —
`investor` · `operator` · `landlord` · `buyer` · `admin` · `common`.

**`screens/api.ts`가 유일한 조회 통로인 이유.** 화면마다 `fetch`를 쓰면 응답 타입이 화면 수만큼
복제된다. 한 파일에 모으면 API 응답 모양이 바뀔 때 고칠 곳이 하나다. 캐시·재요청·로딩 상태도
React Query 한 곳에서 정해진다.

**저장소 구성.**

| 디렉터리 | 무엇 | 스택 | 담당 |
|:---|:---|:---|:---|
| `frontend/` | 웹 화면 + API + 도메인 로직 | Next.js 14 App Router · TypeScript · Tailwind | 웹 |
| `app/` | 운영자 앱 | Expo React Native (Android) | 앱 |
| `contracts/` | 스마트 컨트랙트 | Foundry · Solidity 0.8.24 · OpenZeppelin | 공유 |
| `design/` | Figma 원본(`.fig`)과 화면별 좌표·색·폰트 덤프 | — | 공유 |
| `docs/` | 명세 · 근거 · 계획 | — | 공유 |
| `iot-mock/` · `tools/figma/` | IoT 목업 · Figma 덤프 도구 | — | 공유 |

`frontend/` 규모: 화면 라우트 66개, API 라우트 92개, 도메인 모듈 65개, Prisma 모델 47개.

**배포와 환경.** Vercel(Linux) + Supabase(PostgreSQL). 도커를 쓰지 않는다. 배포는 `frontend/`에서
`npx vercel --prod`, 스케줄은 `/api/cron/reconcile`(`CRON_SECRET` 헤더 검증).

| 묶음 | 키 |
|:---|:---|
| DB | `DATABASE_URL` (6543) · DDL은 5432 오버라이드 |
| 인증 | `JWT_SECRET` |
| 신원 | `IDENTITY_PROVIDER` · `IDENTITY_VERIFIER_URL` · `IDENTITY_VERIFIER_POLICY_ID` · `IDENTITY_CI_SALT` · `OACX_BASE_URL` · `OACX_PROVIDER` |
| 체인 | `ONCHAIN_CHAIN_ID` · `ONCHAIN_RPC_URL` · `ONCHAIN_NAME` · `ONCHAIN_GAS_ZERO` · `ONCHAIN_ESCROW_ADDRESS` · `ONCHAIN_FARM_TOKEN_ADDRESS` · `ONCHAIN_PRIVATE_KEY` |
| 수탁 | `CUSTODY_MASTER_KEY` (32바이트 hex) |
| AI | `GEMINI_API_KEY` · `OPENAI_API_KEY` · `ANTHROPIC_API_KEY` |
| 배치 | `CRON_SECRET` |
| 데이터 | `SMARTFARM_API_KEY` |

**`NEXT_PUBLIC_` 접두사를 함부로 붙이지 않는다.** 빌드 타임에 번들로 인라인되므로 로컬 `.env` 값이
프로덕션에 구워진다. `NEXT_PUBLIC_BASE_URL`에 `localhost:3000`이 박혀 self-fetch가 죽은 적이 있어,
지금은 요청 origin을 쓴다.
