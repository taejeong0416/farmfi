## 2026-08-25 — 박태정

### 배포본을 실제로 눌러 보니 대사식이 이미 깨져 있었다

명세 16장 P0~P2가 전부 코드에 있고 10.6 체인 함수도 9개 중 8개가 배선돼 있어서, 남은 것은
`transferHolding` 과 인수 테스트 자동화뿐이라고 봤다. 배포본을 Playwright 로 직접 조작해
보니 그 판단이 틀렸다. 화면 58개와 쓰기 경로를 돌려 Critical 2건을 포함해 8건이 나왔다.
결과는 `qa/web-qa-sheet.xlsx` 다.

가장 무거운 것은 **거래번호가 다른 두 번째 입금**이었다. 웹훅 멱등은 같은 통지가 두 번 올
때를 막아 준다. 그런데 이미 납입이 끝난 가상계좌로 금액이 같은 입금이 한 번 더 들어오면
그대로 CONFIRMED 가 되어 보유 구좌가 다시 발행됐다. 청약 합 110구좌에 확정 발행 합 210구좌 —
"확정 발행 합 == 청약 합"이 그 자리에서 깨진다. 돈은 실제로 들어왔으므로 없던 일로 만들지
않고, 확정도 발행도 하지 않은 채 관리자 검토로 보낸다.

그 다음이 **화면에 관문이 없었다는 것**이다. API 는 `requireRole` 이 막고 있었지만 페이지에는
아무 검사도 없어서, 투자자 세션으로 `/admin` 을 열면 관리자 메뉴 14개가 "김투자 관리자님"과
함께 그려졌다. 데이터는 API 가 403 으로 막아 대부분 비어 있었으니 유출은 제한적이지만,
명세 2장이 정한 "현재 역할의 메뉴만 표시"는 지켜지지 않았다. 미들웨어가 아니라 레이아웃에
관문을 뒀다 — 시연 계정 판정이 DB 를 읽어야 하는데 미들웨어는 edge 라 prisma 를 못 쓴다.
같은 이유로 `/optimization/[id]` 도 막았다. 그 화면은 서버 컴포넌트가 prisma 를 직접 읽어
API 관문을 지나지 않는다.

`/api/subscribe` 는 화면 어디에서도 부르지 않으면서 적합성·동의·납입을 전부 건너뛰고 보유
구좌를 만들 수 있었다. 청약이 보유 구좌를 만드는 문은 하나여야 해서 지웠다.

QA 자체에 대해 둘 남긴다.

**쓰기 경로를 실제로 눌러야 나오는 것들이었다.** 읽기만 했다면 대사식이 깨지는 것도, 미배정
지점에 증빙이 들어가는 것도 못 봤다.

**데모 리셋은 시연 데이터를 되돌리는 게 아니라 유저 테이블을 비운다.** `seedScenario` 가
재생성 전에 `prisma.user.deleteMany()` 를 돌린다(`seed-scenario.ts:84`). 실제로 가입한 계정과
거기 붙은 OpenDID 검증 기록이 리셋 한 번에 사라진다. 프로덕션과 로컬이 같은 Supabase 를 쓰므로
검증 뒤에는 매번 리셋했고, 그때마다 실계정을 백업했다가 복원해서 이어갔다. 발표 전에 리셋을
한 번이라도 돌릴 계획이면 삭제 범위를 좁힐지 정해야 한다.

**세션 중에 배포가 바뀌면 같은 TC 가 다른 코드를 본다.** 리셋 직후 시연 계정이 없어 이슈로
올렸는데, 뒤에 다시 보니 시드가 정상적으로 만들고 있었다. 그 사이 앱 쪽 커밋이 올라와 재배포된
것으로 보인다. 라운드마다 배포 커밋을 적어 두는 편이 낫다.

### 도면 대조는 지표가 아니라 읽는 법이 먼저다

체크 안 된 97건이 전부 Phase X·Y였다. 계획한 화면과 기능은 이미 닫혀 있었는데 체크박스가
남아 있으니 이어받는 사람에게는 "아직 97개 남았다"로 읽힌다. 체크박스가 진행 상황의 정본이라면
안 할 일에는 체크박스가 없어야 한다. 참고 자료로 내리고 이유를 각 Phase 머리말에 적었다.

숫자를 읽다가 세 번 속을 뻔했고, 그 셋을 읽는 법에 적어 뒀다.

- **합계는 밀림 중앙값을 뺀 나머지를 센다.** `AuthShell` 이 `max-w-modal`(465)과 `px-6`을 함께
  걸어 흰 패널이 417로 좁아지고 24px 밀려 있었다. 여백을 폭 제한 밖으로 빼니 일곱 화면 중
  여섯이 밀림 0 근처로 왔는데 합계는 357→355로 그대로다. 화면이 통째로 제자리를 찾는
  종류의 교정은 이 지표가 못 본다.
- **빈 화면은 어긋남도 0이라 개선처럼 보인다.** 합계가 357→299로 떨어져 좋아했는데 운영자
  화면 다섯이 `맞춘문구 4/N` 로 주저앉아 있었다. Supabase 풀러가 Playwright 동시 요청에
  끊긴 것이다. `맞춘문구` 가 이전과 같은지 확인한 뒤에야 숫자를 읽는다.
- **맞춘 문구 비율이 낮으면 밀림을 읽지 않는다.** `C-I03` 이 `x-79` 로 나빠졌다고 나왔는데
  브라우저로 재보니 도면과 정확히 같았다. 덤프 네 파일에 `C-04` 의 730 패널이 통째로 복제돼
  있어 22개 중 4개만 맞았고, 그 4개로 낸 중앙값이었다.

남은 가로 밀림 셋(`I-07`·`O-02`·`B-06`)은 공통 셸이 아니라 화면 안쪽 구조에서 온다. 고치려면
그 화면을 다시 짜야 하고 발표 동선 밖이라 두었다.

**`npm run seed` 는 돌리지 않는다** — 테이블 44개를 지우고 다시 만드는데 `DATABASE_URL` 이
배포 중인 Supabase 를 가리킨다. 명령 블록에 주의를 붙여 뒀다.

  월일로 만드는 값이라 남의 구독 id 를 알면 계산할 수 있다. 스캔 한 번으로 수령 처리가 되는
  값이 그러면 안 된다. 확인번호(사람이 부르는 값)와 `barcodeToken`(스캔 대상)을 갈랐다.
  같은 회차는 같은 토큰이다 — 명세 B-09 가 "이미지 저장"을 요구하므로 값이 바뀌면 저장해 둔
  이미지가 무효가 된다. 쓴 바코드는 다시 내주지 않는다(`409 PICKUP_BARCODE_USED`).
- **보증서(Q3)** — 정지가 발급 시각을 `null` 로 지우는 것이었고, 그러면 정지와 미발급이 같은
  모양이 된다. 만료는 표현할 자리가 없었다. 상태값 4개를 세우되 **유효기간은 임의로 잡지
  않는다** — 명세 17.1-8 이 "계약 기간과 연동"이라 `OperatorContract.termEnd` 를 쓰고, 모르면
  발급을 거부한다. 만료는 **조회할 때** 처리한다 — 스케줄러를 두면 그게 안 도는 동안 만료된
  보증서가 유효해 보인다. 정지에는 사유 코드가 필요하다(자유 문자열만 받으면 나중에 집계할 수
  없다). 재발급하면 이전 건을 폐기로 닫는다 — 되살릴 수 있으면 폐기가 폐기가 아니다.
- **방문·교육·계약(Q2)** — 셋이 `OperatorApplication` PATCH 하나에 `step` 스위치로 얹혀 있었다.
  예약은 하나만 살아 있게 하고(여러 개면 어느 날 가는지 흐려진다), **진도는 뒤로 가지 않는다**
  (이어보기로 앞부분을 다시 봐도 이미 본 만큼은 본 것이다). 서명 요청과 서명을 나눴다 —
  무엇에 서명하는지 확인한 시점이 없으면 서명 시각만으로는 동의 과정을 설명할 수 없다.
  **상태를 뒤로 밀지 않는다** — 방문 취소가 신청을 `docs` 로 되돌리게 했더니 계약까지 끝낸
  신청도 되돌아갔다.
- **동의(Q1)** — I-03 에 체크박스 세 개가 있었고 문서 이름은 화면 코드에 문자열로 박혀 있었다.
  서버로는 `signature` 한 줄만 갔다. **체크박스는 증거가 아니다.** 문서를 고쳐 쓰지 않고
  `version` 을 올려 새 행을 만든다 — 이미 동의한 사람이 본 문장이 바뀌면 무엇에 동의했는지
  증명할 수 없다. 동의 기록에 해시를 복사해 두는 건 중복이지만, 문서 행을 잘못 건드렸을 때
  동의 시점의 본문이 남는 게 더 중요하다. 묶음 해시는 정렬해서 뜬다 — 정렬하지 않으면 같은
  동의가 호출 순서에 따라 다른 해시를 낸다.

### DB 와 체인을 맞춰보는 경로 (P5)

발행 파이프라인은 자기가 보낸 것만 안다. 보낸 뒤 체인에서 무슨 일이 있었는지는 아무도 확인하지
않았다.

- **Relay 와 각도가 다르다** — Relay 는 "해시가 있으면 성공"으로 본다(재전송을 막으려면 그래야
  한다). 그 가정은 되돌려진 트랜잭션을 성공으로 만든다. `sweepReceipts()` 는 영수증을 실제로
  읽고, revert 면 해시를 **지우고** `CHAIN_FAILED` 로 닫는다 — 해시를 남겨두면 Relay 의
  방어선이 그 건을 확정으로 찍는다.
- **불일치를 고치지 않는다** — 어느 쪽이 맞는지는 기계가 판단할 수 없다. DB 에 맞춰 mint 하면
  이중 발행이고, 체인에 맞춰 DB 를 내리면 투자자 보유가 증발한다. 양쪽 값을 적어두고 멈춘다.
- **큐를 `AuditLog` 에 얹지 않았다** — 감사 로그는 덧붙이기만 하는 이력이라 "아직 안 봤다 /
  봤고 이렇게 처리했다"를 표현할 자리가 없다.
- **같은 불일치가 매일 쌓이지 않게** `scopeKey` 에 unique. 사람이 닫은 건은 다시 열지 않는다.
- **크론은 시크릿 없이 안 열린다** — 대사는 체인을 읽고 발행 상태를 바꾼다.

**남겨둔 제약**: Hobby 플랜은 하루 1회 크론만 받는다. 나머지는 admin 창구의 수동 실행으로 메운다.
**2차 이전이 생기면 깨진다**: 지금 대조식은 "확정 발행 합 == 체인 잔액"이다. `transferHolding`
이 붙는 순간 성립하지 않으므로 이전 이력을 더해 계산하도록 고쳐야 한다.

### 생육 레시피 — 검증 가능한 목표 학습으로

레시피 층이 "환경↔수율에서 최적 생육조건을 찾는다"고 주장하는데 확인할 수단이 없었다. 확인
수단부터 만들고 그 위에서 좌표계·불확실성·목적함수를 고쳤다.

- **합성 반응면이 안장점이었다** — temp×CO₂ 교차항이 오목성 상한의 10배였다. 진짜 최적점은
  표본 상자 모서리에 있었고, 화면 숫자가 그럴듯했던 건 농학 클램프 덕이다. **클램프가
  알고리즘을 검증하는 게 아니라 대체하고 있었다.** 테스트 베드를 분리하고 스펙마다 촐레스키로
  오목성을 자체 검사한다.
- **품종 좌표를 GDD 로 두려다 접었다** — (T−base)/(mid−base) 를 범위폭으로 다시 나누면 base 가
  약분되어 (T−mid)/half 와 같아진다. GDD 가 실제로 필요한 곳은 품종 이전이 아니라 사이클 안의
  시간 적분이다.
- **이전 강도를 곱셈으로만 두면 상한이 안 생긴다** — 정밀도에 w 를 곱하면 w 가 "얼마나 빨리"만
  정하고 "어디까지"를 못 정한다. 품종 불일치를 분산으로 세우니 원 데이터가 무한히 쌓여도
  이전 비중이 정확히 w 로 수렴한다.
- **사전 정밀도가 표본 수의 함수였다** — 잡음이 5배 다른 두 데이터셋이 같은 가중치를 받았다.
  부트스트랩으로 갈았다. 탐색 상자는 원표본으로 고정한다(재표본마다 다시 잡으면 산포에 상자가
  흔들린 몫이 섞인다).
- **목적함수에 비용이 없었다** — 레시피가 수율만 최대화하니 비싼 목표를 정하고 스케줄 층이 그걸
  싸게 달성하는 구조였다. `수익 = 가격×수율(x) − 운전비용(x)` 하나로 합쳤다. 비용이 붙는
  요인은 DLI·CO₂·온도 셋뿐이고 습도·EC·pH 는 비용이 없다는 걸 표에 밝힌다 — 제습 전력과 양액
  원가를 셀 근거가 없어 지어내지 않았다.
- **갭 분석이 부분합과 전체를 어긋나게 내놓고 있었다** — 섀플리 분해로 바꿔 항등식이 되게 했다.
  `max(0, …)` 클램프도 없앴다 — 한 요인만 옮기면 손해인 경우가 실제로 있다.
- **진단 셋을 표면에 붙였다** — 안장점이면 권고를 내지 않고, 최적점이 탐색범위 끝에 붙으면
  경계해로 표시한다("여기가 최적"이 아니라 "여기까지만 봤다"). 표본이 파라미터의 2배에 못
  미치면 R² 는 0이 아니라 null 이다 — 0은 설명력 없음이라 판정 불가와 뜻이 다르다.

### 생육 모니터링 — 광량을 일적산으로, 생장을 환경의 함수로

"생장 모니터링"인데 화면이 전부 환경 센서값이었고, 광량 판정이 최적화와 정면으로 충돌하고
있었다. 실데이터가 없다는 제약이 오히려 순서를 정했다 — 탐지기를 더 만들기 전에 **시드가
탐지기가 잡을 현상을 담고 있는지**부터 봐야 했다.

- **시드 시나리오화** — 세 고장을 시간축에 심었다(냉방 저하는 CUSUM 만, 펌프 막힘은 Z-score+
  게이트, LED 열화는 DLI 만 잡는다). `growthRate` 를 날짜 함수에서 **환경 함수**로 바꿨다.
- **광량 판정 전환** — 최적화가 광주기를 심야로 옮기는데 모니터링은 순간 조도 상한만 봤다.
  심야 점등이 오탐이 되고 LED 열화는 안 걸린다. **생육일 일적산(DLI) 달성률**로 판정하고,
  생육일 경계는 자정이 아니라 **가장 어두운 시각**으로 뒀다 — 점등 블록이 어디로 옮겨가든 한
  버킷에 담기게.
- **2단 밴드** — 최적대 이탈은 주의(제어루프가 되돌림), 고장 게이트 이탈은 심각(사람이 감).
  두 기준이 서로 다른 표를 쓰고 있어 `crop-profiles` 를 단일 출처로 뒀다.

### CUSUM 드리프트 — 회귀 테스트가 드러낸 오탐

"무고장 시드에서 전 센서 드리프트 탐지"가 나왔다. 원인이 셋 겹쳐 있었다.

- **lag 미전달** — 기본 lag=24 는 시간당 표본 전제인데 30분 데이터에 그대로 호출해 12시간
  차분이 되어 일주기를 역위상으로 증폭했다.
- **차분 자체가 원인** — lag 를 고쳐도 오탐이었다. 차분은 저주파 흔들림을 lag 길이의 동일부호
  런으로 바꾸는데 그게 정확히 관리도가 잡도록 설계된 패턴이다. **일중앙값**에 차분 없이 관리도를
  건다(평균은 단발 스파이크에 오염된다).
- **관리한계 고정** — H=5 의 ARL₀ 가 465표본이라 2,880표본 창에선 오경보가 확정이다. 관리이탈점을
  걸러낸 관리상태 표본 부트스트랩으로 한계를 잡는다.

무고장 오경보 60일 5%·30일 0%·7일 0%, 냉방저하는 12일차로 특정(통계량 88.6 vs 한계 ~10).
