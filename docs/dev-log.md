### 웹 프론트 — Figma 62개 화면 이식 + 신규 백엔드

Phase A~K를 끝냈다. 화면과 그 화면이 돌아가는 데 필요한 모델·API를 짝으로 만들었다. 판단이 갈렸던 지점만 남긴다.

- **Tailwind 토큰은 덧붙이는 쪽으로**: `text-base`·`rounded-lg` 같은 기본 스케일을 Figma 값으로 덮어쓰면 아직 안 옮긴 화면의 글자 크기가 같이 흔들린다. 대신 `text-11`~`text-28`, `rounded-6`~`rounded-14`처럼 실측값을 그대로 쓰는 키를 새로 얹었다. Figma 덤프의 숫자가 클래스명에 그대로 보여 대조하기도 쉽다.
- **헤더·푸터는 layout에서 한 번만**: Figma는 모든 화면에 같은 상단바를 그렸다. 화면마다 헤더를 넣는 대신 `layout.tsx`의 `SiteHeader`·`AppFooter`로 한 곳에 뒀고, 로그인 역할에 따라 진입 링크만 바뀐다.
- **C-04는 역할을 바꾸지 않는다**: 이용 목적 선택 화면이 계정 역할을 바꾸는 것처럼 보이지만, Figma 문구가 "로그인한 계정으로 투자·정기구독·운영 서비스를 이용할 수 있어요"다. 한 계정이 셋 다 쓴다는 뜻이라 이 화면은 라우팅만 한다. `PATCH /api/auth/me`는 건드리지 않았다.
- **`Investment`는 청약을 감싼다**: 다단계 신청 상태를 새 파이프라인으로 만들지 않고, 마지막 납입 단계에서 기존 `executeSubscription`을 호출하고 결과만 기록한다(`lib/investment.ts`). 잔액·재고·연간한도 검증이 한 곳에 남는다.
- **증빙 게이트는 기존 상태 어휘에 얹었다**: 계획서의 대문자 상태(`EVIDENCE_SUBMITTED` 등)를 그대로 쓰면 소문자 상태를 쓰는 기존 verify·complete·timeout 라우트와 앱이 전부 깨진다. `evidence_submitted`·`revision_required` 두 개만 추가하고 나머지는 기존 이름을 살렸다. 집행 게이트는 이미 `complete`가 `verified`만 통과시키므로 그대로 둔다.
- **운영자 7단계는 모델 하나에**: 방문 예약·교육 이수·공간 확정·계약 서명마다 모델을 세우는 대신 `OperatorApplication`에 필드를 붙이고 `PATCH ?step=`으로 밀었다. 앞 단계가 안 끝나면 다음 단계를 거부한다.
- **정기구독 회차를 미리 만든다**: 매장에서 보여줄 확인번호가 회차마다 필요해서, 신청 시점에 앞으로 4회차를 `PickupOrder`로 만들어 둔다. 확인번호는 구독 id와 날짜에서 계산해 재발급해도 같은 값이 나온다.
- **구매자용 재고 조회는 따로**: `/api/inventory`는 operator 전용이라 구매자가 부를 수 없다. 수치를 그대로 내리는 대신 "고를 수 있는지"만 담은 `/api/subscriptions/catalog`를 새로 뒀다.
- **A-15는 감사 로그에서 뽑는다**: AML 화면의 데이터 원천이 따로 없다. 이상거래를 지어내는 대신 감사 로그에서 기한 초과·검증 반려·하루 다건 청약을 골라 보여준다. 연간한도 초과와 본인확인 미완료는 API에서 이미 거부되므로 목록에 오르지 않는다고 화면에 적었다.
- **금지 용어는 화면·응답·감사 로그까지**: `.tsx` 전체에서 0건. `Escrow`·`TokenHolding`·`Dividend` 모델명과 기존 라우트의 설계 주석은 남는다 — 모델명을 바꾸려면 데이터 마이그레이션이 따라야 해서 v2.1 모델 정리로 넘겼다. 범위는 `build-plan.md` 맨 끝에 적어뒀다.
- **없는 화면은 리다이렉트로**: 지갑 등록·재연결 URL은 만들지 않고 `middleware.ts`에서 `/verify/account`로 보낸다. `/verify-identity`도 새 흐름으로 넘긴다.

### 운영자 앱 프론트 — Figma 36개 화면 이식

Phase L·M을 끝냈다. 백엔드는 손대지 않고 화면만 옮겼다. 판단이 갈렸던 지점만 남긴다.

- **EC 대신 pH**: Figma 베드 카드·센서 타일에 EC 칸이 있는데 `IotData`가 수집하는 값은 `phLevel`이다. EC 라벨을 달면 없는 값을 있다고 말하게 되므로 pH로 표기했다. EC를 실제로 수집하기 시작하면 `SENSOR_META`에 키를 추가하면 된다.
- **센서는 지점 단위**: Figma는 베드 4개가 각각 다른 판독을 가진 것처럼 그렸지만 센서는 프로젝트 단위로 저장된다. 베드마다 값을 흩뿌리는 대신 08 화면 상단에 "환경 센서는 매장 단위로 수집됩니다"라고 적고 같은 값을 보게 뒀다.
- **쓰기 경로가 없는 동작**: 관찰 기록·일정 등록·재고 조정·품목 등록·설비 제어·임계값 저장·알림 설정·리포트 내보내기는 API가 없다. 버튼을 죽이는 대신 화면 안에서 반영하고, 팝업이 "이 기기에만 반영됩니다 · 서버 저장은 ○○ API 연결 후"라고 밝힌다. 흐름은 데모할 수 있고 거짓말은 하지 않는 선.
- **21 제어 실패의 조건**: 실패 화면을 만들려고 실패를 지어내지 않았다. 센서 응답이 `stale`인 지점은 설비가 실제로 바뀌었는지 확인할 길이 없으므로, 그 경우에만 제어 실패로 처리한다.
- **일정은 재고에서 만든다**: 일정 API가 없어 06 재배 일정은 `Inventory`의 `plantedAt`·`expectedHarvestAt`에서 파종·수확 일정을 만든다. 별도 모델을 세우기 전까지는 이게 실제 데이터다.
- **픽셀 에셋은 남긴다**: 픽셀아트 화면 8개는 새 화면이 대체해 지웠지만 스프라이트 자체는 Figma가 비워둔 자리(`이미지 준비 중`·`Bed thumb (교체)`·`SceneCard`·`MiniPlants`)에 그대로 들어간다. `components.tsx`는 그 시각 요소만 남기고 껍데기·탭·상태 표시는 `ui/`로 넘겼다.
- **기기 크롬은 안 옮긴다**: Figma의 Status Bar·Home Indicator 프레임은 목업이다. 실제 기기에서는 OS가 그리고 `SafeAreaView`가 자리를 잡는다. 색 치환표의 판단 보류였던 `#070428`은 이 결정으로 함께 사라졌다.

**미결**: `src/components/app-tabs.web.tsx`가 존재하지 않는 `/explore` 라우트를 가리켜 `npx tsc --noEmit`이 실패한다. Expo 템플릿 잔재로 어디서도 import되지 않는다. 앱의 타입 검증을 깨끗하게 하려면 지워야 한다.

### 스모크에서 잡힌 것
`tsc`만으로는 안 보이는 것들이 실호출에서 나왔다. dev 서버 + admin Bearer로 신규 라우트 전부 왕복(상태를 원위치로 되돌리는 시나리오만) 후 흔적 정리.
- **이의제기가 통과한 마일스톤에도 열렸다**: `retryCount>0`만 봐서, 1회 실패 후 재검증을 통과한 `verified` 건이 접수 대상에 들어갔다. `verified`·`completed` 제외로 수정.
- **운영자 정산 라인이 안 생겼다**: 코드가 아니라 데이터 — 시드가 돌던 시점엔 `Project.operatorId`가 없어 기존 행이 전부 null이었다. 시드 정의와 같은 값(정하은)으로 백필하고 재확인 → `매출 1,400,000 − 이용료 200,000 − 임대료 500,000 = 700,000` 생성.
- **구간 전환 확인**: `breakEvenRevenue=1,400,000`·적자 0.8 규칙에서 매출 100만 → `band=deficit`, 배당 262,857(= 풀 328,571 × 0.8). 규칙 삭제 후 기본값 0.6 복귀도 확인.
- 가드 확인: 사유 없는 중지·최종판정, 1 초과 비율, 잘못된 상태 전이, 중복 이의제기, 완료 건 재지급 — 전부 4xx.

## 2026-08-03 — 박태정

### 생육 모니터링 — 광량을 일적산으로, 생장을 환경의 함수로
"생장 모니터링"인데 화면이 전부 환경 센서값이었고, 광량 판정이 최적화와 정면으로 충돌하고 있었다. 실데이터가 없다는 제약이 오히려 순서를 정했다 — 탐지기를 더 만들기 전에 **시드가 탐지기가 잡을 현상을 담고 있는지**부터 봐야 했다.

- **시드 시나리오화**(`iot-seed.ts`): 기존 시드는 2% 무작위 단발 스파이크뿐이라 CUSUM은 탐지할 대상이 없고 DLI는 매일 같은 값이었다. 세 고장을 시간축에 심음 — 12~18일차 냉방 저하(하루 +0.6℃, CUSUM만 잡음) / 30일차 펌프 막힘(pH 4.2, Z-score+게이트) / 45일차~ LED 열화(−28%, DLI만 잡음). `growthRate`를 날짜 함수에서 **환경 함수**로 교체: GDD로 진행하고 DLI 부족분만큼 지연.
- **광량 판정 전환**: 최적화(`dliSchedule`)가 광주기를 심야로 옮기고 시간 압축 시 PPFD를 올리는데, 모니터링은 순간 조도 상한만 봤다 → 심야 점등이 오탐이 되고 LED 열화는 안 걸림. 광량을 순간값 판정에서 빼고 **생육일 일적산(DLI) 달성률**로 판정. 생육일 경계는 자정이 아니라 **가장 어두운 시각** — 점등 블록이 어디로 옮겨가든 한 버킷에 담기게.
- **2단 밴드**: `iot-health.HEALTHY_RANGES`와 `crop-profiles.healthyRanges`가 서로 다른 기준을 쓰고 있었다. crop-profiles를 단일 출처로 두고 `faultRanges()`가 여유폭을 더해 고장 게이트를 파생. 최적대 이탈=주의(제어루프가 되돌림) / 게이트 이탈=심각(사람이 감).
- **GDD 수확 예측**: 적산은 광 제약을 반영한 유효 GDD로 쌓는다(온도만 세면 광 부족한 날도 만근으로 잡혀 진행률이 실제 생장을 앞지름).
- **알림 배선**: `iot/generate`가 Z-score 이상일 때만 Notification을 만들고 있었다. 화면과 같은 `analyzeGrowthMonitoring`을 태워 고장 게이트·CUSUM 드리프트·DLI 미달까지 통지(6시간 쿨다운).

### CUSUM 드리프트 탐지 — 회귀 테스트가 드러낸 오탐 3건
회귀 테스트를 쓰자 "무고장 시드에서 전 센서 드리프트 탐지"가 나왔다. 원인이 셋 겹쳐 있었음:
- **lag 미전달**: `cusumDrift`의 기본 lag=24는 시간당 표본 전제인데 모니터링이 30분 데이터에 그대로 호출 → 12시간 차분이 되어 일주기를 역위상으로 증폭.
- **차분 자체가 원인**: lag를 고쳐도 오탐. 차분은 저주파 흔들림을 lag 길이의 동일부호 런으로 바꾸는데(측정 acf(24)=−0.57) 그게 정확히 관리도가 잡도록 설계된 패턴. → **일중앙값**에 차분 없이 관리도를 건다(평균은 단발 스파이크에 오염됨).
- **관리한계 고정**: H=5의 ARL₀가 465표본이라 2,880표본 창에선 오경보가 확정. Siegmund 근사로도 부족(i.i.d. 전제 불일치) → 관리이탈점(|z|>3)을 걸러낸 **관리상태 표본 부트스트랩**으로 한계를 잡음.
- **잘린 부분일**: 오경보가 전부 마지막 버킷에서 나왔다. DLI가 쓰던 `complete` 기준을 관리도에도 적용.
- **결과**: 무고장 오경보 60일 5%·30일 0%·7일 0%, 냉방저하는 12일차로 특정(통계량 88.6 vs 한계 ~10). 회귀 테스트 16건 추가 — 전체 50건 통과.
