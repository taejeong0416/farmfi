### 1. 프로젝트 소개

#### 1.1. 개발배경 및 필요성

**공간 문제 — 공실은 회복되지 않고 있다**

부산대 앞 상권 소규모 상가 공실률은 **18.8%(2026.1Q)** 로 부산 평균 7.8% · 전국 평균 8.3%를 크게 웃돈다. 전국 대비 2배 이상, **전국 5위 · 부산 1위(2025 기준)** 수준이다. 추이를 보면 부산대는 25.6% → 23.4% → 25.2% → 18.8% → 18.8%로 3년째 높은 수준에서 회복되지 못하고 있다. *(한국부동산원 「상업용부동산 임대동향조사」)*

**시장 문제 — 오프라인 매장의 필요성이 낮아졌다**

부산대 상권 주력 업종은 **요식업 41.7% · 소매업 24.0%** 다. 두 업종이 상권의 3분의 2를 차지한다. 그런데 이 주력 업종의 소비가 온라인·매장 밖으로 이동 중이다.

- 요식업 폐업률은 **17.5%(2026)** 로 상승 후 고착. 코로나19 이후 외식 소비가 개인화·파편화되며 간편식·집밥이 외식 수요를 대체하고 있다.
- 소매업은 **2025 상반기 소매시장 성장률 역대 최저 0%**, 대형마트는 전년 대비 **-0.4% 역성장**.

즉, 기존 업종 그대로 공실을 다시 채우면 또다시 비워질 확률이 높다.

**공급 문제 — 정부 지원만으로는 한계가 있다**

정부는 공실 해소를 위해 도시재생 사업을 시행해 왔지만 자립적인 운영주체와 수익모델이 없어 한계가 있다. (사례: 14곳 한시 개방, 10곳은 여전히 공실)

> "거점시설 활성화의 최우선 요인은 자체 수익이며, 자립적 재원 역량을 갖춘 민간조직의 초기 참여가 필요하다."
> — 도시재생 거점시설 중요요인 연구, 한국지역개발학회지

→ **결론:** 공실에 들어오는 점포는 일시적 입점을 넘어 스스로 수익을 내며 지속 운영될 수 있어야 한다.

#### 1.2. 개발목표 및 주요내용

FarmFi는 비어 있는 도심 공실에 민간 투자금을 모아 스마트팜 설비를 설치하는 플랫폼이다. 지역 운영자가 재배·판매를 맡으면 그 공실은 주민에게 24시간 신선채소를 파는 매장이 된다. 공간과 운영자, 자본과 기술이 흩어져 연결되지 못하던 시장을 하나의 매장 프로젝트로 묶는 것이 핵심이다.

**핵심 컨셉 — "웹으로 연결하고, 앱으로 운영하며, 매장에서 판매한다"**

| 레이어 | 제품 | 역할 | 주 사용자 |
|:---:|:---:|:---|:---|
| 연결 | **FarmFi 웹** | 공간·자본·운영자를 하나의 프로젝트로 연결 | 투자자, 운영자, 소비자 |
| 운영 | **FarmFi 앱** | 스마트제어로 생육·재고·판매 통합 관리 | 운영자 |
| 판매 | **FarmFi 매장** | 주민이 방문해 필요한 만큼 직접 구매 | 소비자 |

```
[ FarmFi 웹 ]  ──연결──▶  [ FarmFi 앱 ]  ──운영──▶  [ FarmFi 매장 ]  ──판매──▶  주민
   투자자·자본                 운영자·생육                  공실 → 상시 매장
   운영자·공간                 재고·판매 관리                무인결제 / 정기구독
   소비자·구독
```

**서비스가 만족시키는 세 가지 가치**

- **즉시** — 온라인이 대체할 수 없는, 지금 바로 사는 오프라인 경험
- **소량** — 최소주문금액·배달비 부담 없이 필요한 한두 끼 분량만 구매
- **품질** — 스마트팜 재배로 계절·기후에 흔들리지 않는 안정적 신선도

**이번 산출물의 범위** — MVP 2종. ① FarmFi 웹(연결) · ② FarmFi 앱(운영), 그리고 오프라인 매장(판매).

#### 1.3. 세부내용

**지속 운영 점포의 3대 조건**

FarmFi의 아이템은 감(感)이 아니라 "어떤 점포여야 공실에서 살아남는가"라는 질문에서 역산해 도출되었다.

| 측면 | 문제 상황 | 필요 조건 |
|:---:|:---|:---|
| 시장 | 온라인으로의 소비전환 심화 | **온라인 한계가 뚜렷한 업종** |
| 수요 | 한정된 상권의 고객 규모 | **일상에서 반복 구매되는 생활 밀착형 제품** |
| 공급 | 지속 가능한 자립적 재원 필요 | **외부 지원 없이도 안정적인 공급** |

- **조건 ❶ 실물 확인·즉시성·소량 제공** — 품목별 온라인 침투율에서 **신선·가공식품은 26.2%로 최하위**(가전 53.7%, 가구 49.7%). 온라인에서 신선식품을 사지 않는 이유는 신선도를 확인할 수 없어서 **29.2%**, 배송 중 변질 우려 **15.4%**. 저녁·야간에 채소·과일이 필요했던 경험 **41.1%** 중 **90.9%가 미해결**(참음 43.2%, 새벽배송으로 다음날 29.5%, 다음날 구매 18.2%). 온라인 식료품은 최소주문금액이 높고(쿠팡·배민 15,000원 미만 주문 불가, 컬리 40,000원 이상 무료배송), 주 구매자의 **85.7%가 배달비·최소주문금액에 불만족**.
- **조건 ❷ 반복 구매되는 신선 식품** — 신선식품 구매 고객의 월평균 구매 횟수는 **6.13회**로 비식품 구매 고객(1.63회)의 **약 3.8배**. "신선 채소·샐러드 매장이 생기면"에 **주 1회 이상 이용 의향 42.1%**.
- **조건 ❸ 비계절성·예측 가능한 공급** — 기후에 민감한 신선채소는 **연간 가격 등락률 최대 15.3%**. 스마트팜은 계절·기후 영향을 받지 않는다(롯데마트 스마트팜 농산물 품목수 전년 대비 40% 증가). 스마트팜 재배 즉석샐러드·신선채소 **구매 의향 86.9%**.

> **세 가지 조건을 모두 만족하는 솔루션 = 도심형 스마트팜 기반 24시간 신선식품 매장**

**이해관계자와 가치 순환**

다섯 주체가 참여하는 다면 플랫폼이며 각자가 얻는 가치가 다시 매장의 지속 운영으로 이어진다.

| 이해관계자 | 역할 | 핵심 니즈(Pain) | FarmFi가 주는 가치(Gain) | FarmFi에 제공하는 것 |
|:---:|:---|:---|:---|:---|
| **운영자** | 재배·매장 운영 | 시설 자금·경험 없이 창업 어려움 | 초기 설비 부담 없이 지역 운영 일자리·운영 소득 | 노동·현장 운영 |
| **투자자** | 조성 자본 제공 | 신뢰할 실적·담보 없는 소액 실물투자처 부재 | 운영 성과에 따른 수익 분배·새 지역자산 투자처 | 설비 조성자금 |
| **소비자** | 생활권 구매 수요 | 야간·소량 신선식품 살 곳 없음 | 가까운 매장에서 24시간·소량 신선식품 | 구매 수요(반복 매출) |
| **정부/기관** | 공간·정책 지원 | 자립 운영주체 없는 도시재생의 한계 | 자립적 민간 운영으로 상권 회복 | 유휴 공간·전환 비용 지원 |
| **팜피(플랫폼)** | 공실 전환·운영 지원 | — | 도입·운영·확장 단계별 수익 | 연결·기술·정산 시스템 |

```
              운영성과 수익 분배 ▲
     [투자자] ─────────────────── [FarmFi] ─────────────── [소비자]
        │  조성자금 제공 ▼          공실 전환·운영 지원        │  구매 수요 제공 ▲
        │                              │  │                    │  가까운 신선식품 ▼
        │           일자리·운영 소득 ▲ │  │ 상권 회복 ▲         │
     [운영자] ──── 재배·매장 운영 ▼ ───┘  └── 전환 비용 제공 ▼ ─ [정부]
```

**대표 페르소나**

- **운영자 — 김운영(50대, 중장년 재취업 희망)** : 목돈 없이도 안정적으로 일할 지역 일자리를 원한다. 설비·기술은 부담이지만 앱이 재배를 안내해주면 운영 가능.
- **투자자 — 이자본(30대, 소액 실물투자 관심)** : 부동산·주식 외에 실물 기반의 소액 투자처를 찾는다. 회수 기간·프리미엄이 명확하고 진행 상황을 투명하게 볼 수 있길 원한다.
- **소비자 — 박주민(1\~2인 가구, 상권 인근 거주)** : 저녁 늦게 필요한 한두 끼 분량의 신선채소를 배달비·최소주문 없이 바로 사고 싶다.

**공실 → 상시 매장 전환 8단계 라이프사이클**

| 단계 | 명칭 | 주체 | 핵심 활동 |
|:---:|:---|:---:|:---|
| 01 | 공실 발굴 | 팜피 / 정부 | 전환 대상 유휴 공실 확보 |
| 02 | 프로젝트 개설 | 팜피 | 매장 프로젝트로 등록·공개 |
| 03 | 투자자 모집 | 투자자 | 목표 금액까지 투자 참여 |
| 04 | 운영자 배정 | 운영자 | 자격 확인·교육·계약을 마친 운영자 매칭 |
| 05 | 설비 설치 | 설비업체 | 스마트팜 유닛·매장 설비 시공 |
| 06 | 재배·판매 운영 | 운영자 | 앱으로 생육·재고·판매 관리 |
| 07 | 주민 방문·구매 | 소비자 | 매장 방문 또는 정기구독 수령 |
| 08 | 성과 확인·배분 | 팜피 / 투자자 | 매출 정산 후 투자자에게 수익 배분 |

**매장 공간 구성 — 30평 스마트팜 매장**

매장은 **8개 재배 유닛(3단 × 8구)** 을 중심에 두고 판매와 재배, 세척과 설비 공간을 함께 배치한다.

| 구역 | 면적 | 용도 |
|:---:|---:|:---|
| ① 판매·결제 | 18㎡ | 상품 진열·무인 결제(키오스크), 입구 |
| ② 스마트팜 | 50㎡ | 스마트팜 8유닛(3단×8구) 재배, 중앙 작업 통로 0.9m |
| ③ 세척·제조 | 19㎡ | 세척·상품 제조(샐러드·믹스팩 구성) |
| ④ 공조·설비 | 12㎡ | 확장 설비실·공조 |

**운영자가 프로젝트를 여는 과정**

프로젝트는 팜피가 임의로 열지 않는다. 운영자가 자기 매장 조건으로 수익성을 따져 본 뒤 감당 가능한 투자안을 골라야 열린다.

| 순서 | 하는 일 | 나오는 값 |
|:---:|:---|:---|
| ① | 매장 조건 입력 — 유닛 수·판매가·운영비 | 팩당 마진, 월 배분 가능 이익이 자동 산출된다 |
| ② | 투자안 선택 — **연 프리미엄 × 회수기간** 조합 | 조합마다 조건이 다르다 (6\~12% × 12\~30개월) |
| ③ | 선택한 투자안을 **하루 필요 판매량**으로 환산 | "이 조건을 맞추려면 하루 몇 팩을 팔아야 하는가" |
| ④ | 유닛 생산 기준선(26팩/일)과 대조 → **신호등** | 🟢 개설 권장 / 🟡 공지 후 개설 / 🔴 개설 불가 |
| ⑤ | 🟢·🟡이면 프로젝트 개설 → 투자자 모집 시작 | 투자자는 이 투자안을 보고 참여를 결정한다 |

운영자는 투자 매력도와 판매 부담을 저울질해 투자안을 정한다. 프리미엄을 올리면 투자자는 모이지만 팔아야 할 양이 늘어난다. 회수기간을 늘리면 부담은 줄지만 투자자 입장에서 회수가 늦어진다. 이 상충을 숫자로 보여주는 것이 아래 표다.

**투자자가 돈을 회수하는 과정**

| 순서 | 하는 일 |
|:---:|:---|
| ① | 열린 프로젝트의 투자안(연 프리미엄·회수기간)을 확인하고 참여 |
| ② | 매장이 운영을 시작하면 월 단위로 매출을 집계 |
| ③ | 매출에서 변동비·고정비를 뺀 **배분 가능 이익**을 산정 |
| ④ | 보유 구좌 비율대로 매달 배분 — 웹 `수익 상세`에서 이번 달 예상 회수액·회수 예정일·월별 회수 내역(지급완료/회수예정/지급실패)을 본다 |
| ⑤ | **원금 + 프리미엄을 다 회수하면 배당 종료(엑싯)** |
| — | 매장 수익이 계획에 못 미치면 회수기간을 **최대 36개월까지 연장**하고, 그래도 안 되면 **설비 처리대금의 90%** 를 투자자에게 지급 |

**단위경제 — 매장 1개 기준** (검정=운영자 입력값, 초록=자동 산출값)

| 항목 | 값 | 비고 |
|:---|---:|:---|
| 유닛 개수 | 8개 | 스마트팜 유닛 |
| 월 판매량 | 792팩/월 | 하루 약 26팩 (월 생산량 110팩/유닛 × 판매율 90%) |
| 판매가 | 11,000원/팩 | 토핑(삶은 달걀·스위트콘·방울토마토)+드레싱 포함 |
| 팩당 변동비 | 1,500원/팩 | |

#### 1.4. 기존 서비스(상품) 대비 차별성

**시장에는 "연결 주체"가 없다.** 매장 전환에는 4가지 핵심 요소가 필요하지만 각 요소는 공백을 안은 채 서로 연결되지 못한다.

| 보유 주체 | 필요 요소 | 연결의 공백 |
|:---|:---:|:---|
| 장기 공실(임대인) | 공간 | 안정적인 운영자 공백 |
| 실물자산 투자자 | 자본 | 신뢰할 실적·담보 공백 |
| 일자리 수요자 | 운영자 | 시설 자금·경험 공백 |
| 스마트팜 설비업체 | 기술 | 매장화 경로 공백 |

→ **FarmFi는 이 네 요소를 하나의 매장 프로젝트로 연결하는 주체가 된다.**

| 비교 항목 | 기존 공실 지원 사업 | 일반 스마트팜 SW | 일반 POS | **FarmFi** |
|:---|:---|:---|:---|:---|
| 자금 집행 | 일괄 지급 | 해당 없음 | 해당 없음 | **마일스톤 단계 집행** |
| 집행 근거 | 운영사 판단 | 해당 없음 | 해당 없음 | **AI 다중신호 검증 + 체인 기록** |
| 관리 대상 | 자금만 | 재배만 | 판매만 | **재배 ↔ 판매 ↔ 자금 연결** |
| 운영 주체 | 자립 모델 부재 | 해당 없음 | 해당 없음 | **자격·교육·보증서를 갖춘 지역 운영자** |
| 기관 보고 | 없음 | 없음 | 없음 | **공실전환·생산·판매 성과 리포트** |
<br/>

#### 1.5. 사회적가치 도입 계획

비어 있던 공간을 투자와 일자리, 기술이 함께 성장하는 선순환 지역 생태계로 전환한다.

| # | 임팩트 | 내용 |
|:---:|:---|:---|
| ❶ | 공간의 회복 | 공실을 생활거점으로 전환해 신선식품 접근성·상권 활력 향상 |
| ❷ | 일자리의 확장 | 중장년층이 안정적으로 참여할 수 있는 지역 운영 일자리 창출 |
| ❸ | 자본의 참여 | 매장 운영성과에 따라 수익을 배분받는 새로운 지역자산 투자처 제공 |
| ❹ | 기술의 성장 | 현장 실증·데이터 축적으로 설비를 고도화하고 후속 시장 확대 |

**확장 로드맵** — 한 매장에서 검증한 모델을 여러 매장으로 확장할수록 팜피의 반복 매출이 커진다.

| 규모 | 단계 | 핵심 |
|:---:|:---:|:---|
| **매장 1개** | 검증 | 수익성·운영 프로세스 검증, 초기 구축매출 발생 |
| **매장 5개** | 1차 확장 | 시스템 이용료·운영관리 매출 누적, 표준 운영 프로세스 적용 |
| **매장 15개 이상** | 2차 확장 | 다점포 통합관리, 정산·성과보고 자동화, 반복매출 중심 구조 정착 |

> **전기차가 이동의 표준을 바꾸었듯, FarmFi는 공실 전환의 표준을 바꾼다.**

### 2. 상세설계

#### 2.1. 시스템 구성도

```
[ 사용자 채널 ]
   투자자·구매자 웹  (Next.js 14 App Router)
   운영자 앱        (Expo React Native)
        │
        │  HTTPS · 세션 — 웹은 쿠키, 앱은 Bearer
        ▼
[ FarmFi 서버 — Next.js API Routes (Vercel) ]

   본인인증·보증서   OmniOne CX 신분증 본인확인 → Open DID Verifier
                     운영자 보증서(VC) 발급
   자금·집행         투자 신청 게이트 → 에스크로 분리보관
                     → 5단계 마일스톤 집행 → 설비업체 직불
   AI 게이트         Gemini Vision·OCR — 계약서·발주서·설치사진·검수확인서
                     문서 간 교차검증 → 통과분만 집행
   운영·최적화       생육 모니터링 · 재고-생산량 연동 · 판매성과 리포트
                     생육레시피 · 에너지·생산량 최적화
   정산·지급         매출 집계 → 배분 가능 수익 계산 → 지급 API Adapter
   기록 중계         Outbox → Chain Relay (운영지갑이 서명)
        │
        ├─▶ [ 데이터 ]     Supabase PostgreSQL — 계정·검증결과·역할 정보
        │                  Supabase Storage — 증빙 원본, SHA-256 해시로 대조
        │
        ├─▶ [ 외부 연동 ]  은행·PG(토스페이먼츠) — 가상계좌 발급·입금 확인
        │                  스마트팜 API·센서 — 생육 데이터 수집
        │
        └─▶ [ 기록 원장 ]  OmniOne Chain (BESU) — 가스 0, 운영지갑 서명
                           Escrow · FarmToken · Dividend · RoundGate
                           ProjectRegistry · AuditTrail
                           Custody Wallet — 1인 1지갑, AES-256-GCM 봉인
```

**원칙** — 원화는 금융기관 계좌에 보관하고 블록체인에는 자금의 배정·집행·정산 상태와 결과를 기록한다. 사용자는 지갑 주소·개인키·가스비를 직접 다루지 않는다(서버 Custody 방식).
<br/>

#### 2.2. 자금 흐름 3단계

FarmFi의 신뢰 구조는 **투자모집 → 자금집행 → 수익정산** 세 단계로 작동한다.

**❶ 투자모집 — 지갑 발급과 권한 부여**

| 단계 | 기술 요소 | 역할 |
|:---|:---|:---|
| 모바일 신분증 인증 | OmniOne CX | 신분증 인증 화면 제공·결과 전달, 유효성·본인 여부 검증 |
| 참여자 자격 확인 | Open DID Issuer / Backend Auth | 운영자 보증서를 VC로 발급, 투자자·운영자 참여 가능 여부 판정 |
| 지갑 연결 | Custody Wallet / AES-256-GCM | 서버가 1인 1지갑 생성·보관, 개인키 봉인 후 DB에는 참조값만 저장 |
| 역할별 권한 부여 | RBAC / PostgreSQL | 투자자·운영자·관리자 역할별 기능 접근 구분·저장 |

**❷ 자금집행 — 토큰 발행과 증빙 기반 지급**

투자금이 입금되면 같은 금액의 토큰을 발행해 해당 매장에 배정하고 등록된 증빙을 코드가 확인한 뒤 실제 지급이 완료된 결과만 체인에 기록한다.

| 단계 | 기술 요소 | 역할 |
|:---|:---|:---|
| 투자자 원화 입금 | 금융기관·PG API / Payment Webhook | 입금·결제 처리, 입금 성공·실패 결과 수신 |
| 입금 내역 확인 | Payment Service / Idempotency Key | 입금액·신청자·프로젝트 대조, 중복 처리 방지 |
| 집행 토큰 발행·배정 | Execution Token Contract / BESU Free Gas Network | 입금액에 대응하는 토큰 발행, 매장에 배정·잔액 관리 |
| 마일스톤 증빙 제출 | Object Storage / SHA-256 Hash | 계약서·발주서·설치사진 원본 저장, 해시로 변경 여부 검증 |
| 조건 대조·집행 승인 | Escrow Contract / Backend Rule Engine | 단계별 집행 비율·순번 강제(앞 단계 미완료 시 거부), 증빙 자동 대조 |
| 계좌에서 원화 이체 | Bank Transfer API / Idempotency Key | 설비업체 계좌로 지급, 응답 없으면 재송금 대신 결과 조회 |
| 집행 결과 체인 기록 | Outbox·Chain Relay | 이체 결과 저장·서명 후 BESU 전달, 지급 성공 금액만 집행 완료 처리 |

**투자금 사용 마일스톤**

| 단계 | 집행 비율 | 누적 | 검증 신호 |
|:---|---:|---:|:---|
| 1. 계약 체결 | 10% | 10% | 공간사용 협약서 · 임대계약서 |
| 2. 설비 발주·제작 | 20% | 30% | 설비 발주서 · 계약금 영수증 (교차검증) |
| 3. 반입·설치 착수 | 30% | 60% | 반입 현장 사진 · 운송 영수증 (교차검증) |
| 4. 설치 완료·검수 | 25% | 85% | 설치 완료 사진 · 검수확인서 (교차검증) |
| 5. 시운전·영업 개시 | 15% | 100% | 센서 데이터(가동률) · 첫 판매 영수증 |

각 단계 증빙이 확인되면 해당 비율만큼 에스크로에서 설비업체에 직접 지급되며 운영자는 현금을 선지급하지 않는다. 초반(계약)은 낮게 잡아 투자자 리스크를 줄이고 하드웨어가 현장에 들어오는 반입 시점(누적 60%)에 대금을 크게 실어 설비업체의 외상 구간을 좁힌다. 마지막 15%는 실제 개점까지 확인한 유보금으로 남긴다.

**❸ 수익정산 — 투자 비율 기반 배분**

| 단계 | 기술 요소 | 역할 |
|:---|:---|:---|
| 매장 매출 집계 | POS·PG API / PostgreSQL | 결제·취소·환불 수집, 일별·상품별 판매 저장 |
| 배분 가능 수익 계산 | Settlement Engine / Settlement Rule Table | 매출에서 운영비·수수료 반영해 배분액 산정 |
| 투자자별 수익 배분 | FarmToken 보유 원장 / ProjectRegistry | 투자자별 구좌·배당 시점 잔고 스냅샷, 연 프리미엄·회수기간·원금 체인 고정 |
| 투자자 계좌로 지급 | Bank Transfer API / Outbox·Chain Relay | 수익금 원화 지급, 결과·누적 수익 체인 기록 |

> **집행과 정산의 분리** — 마일스톤(증빙 기반)은 매장 "조성자금 집행"에만 적용하고 투자수익은 매장 "운영실적과 투자 비율"을 기준으로 별도 정산한다.

**참여자 안전장치**

| 주체 | 장치 |
|:---:|:---|
| 투자자 | 자금 집행은 단계별 증빙 확인(에스크로) 후에만 이뤄지며, 지급 성공이 확인된 금액만 집행 완료로 확정된다. 매장 수익이 나지 않을 경우 **최대 36개월까지 회수기간을 연장**하고, **설비 처리대금의 90%를 투자자에게 지급**한다 |
| 설비업체 | 설비 **소유권은 대금 완납 전까지 유보**하며, 프로젝트가 중단되면 모듈형 스마트팜 유닛을 회수해 재판매·타 매장 재배치한다. 미집행 잔여 재원(에스크로)은 중단 시 설비업체 미회수 대금 보전에 우선 배정한다 |
| 운영자 | 현금 자기부담 없이 노동·성과연동 보수·운영보증서로 책임을 진다. 이탈·부실 운영 시 설비를 철거하지 않고 **필수교육·보증서를 마친 대기 운영자 풀에서 교체**해 매장과 자산을 유지한다 |

### 3. 개발결과

#### 3.1. 전체시스템 흐름도

- **유저 플로우** — 공실 하나가 투자·운영을 거쳐 주민이 찾는 상시 매장이 되기까지

```
[1] 투자자 본인인증 (OmniOne CX · Open DID) → 실명·연령·투자한도 판별
        ↓
[2] 투자 신청 → 가상계좌 입금 → 투자금 분리보관
        ↓
[3] 공간 진단·선별 → 운영자 모집 → 1공간 1운영자 배정
        ↓
[4] 마일스톤 증빙 제출 (계약서·발주서·설치사진·검수확인서·IoT)
        ↓
[5] AI 멀티시그널 검증 + 교차검증 → 통과 시에만 체인 기록
        ↓
[6] 단계별 집행 — 에스크로 → 설비업체 직불
    (1단계 10% → 2단계 20% → 3단계 30% → 4단계 25% → 5단계 15%)
        ↓
[7] 운영 개시 — 스마트팜 재배 + 24시간 무인 판매
        ↓
[8] 생육 모니터링 · 재고-생육 연동 · 판매-재배 연동
        ↓
[9] 정산 → 수익 배분 → 기관 성과 리포트
```

- **태스크 플로우 — 마일스톤 집행 (자금이 실제로 나가는 구간)**

```
운영자·설비업체 증빙 업로드
   → SHA-256 해시 계산·저장
   → AI 판독 (신호별: 계약서 / 영수증 / 사진 / 검수확인서 / 센서)
   → 문서 간 교차검증
   → 전부 통과?
        ├ 예  → 단계 verified → 관리자 항목별 확인 → 집행 → 체인 기록
        └ 아니오 → 보류. 보완 요청. 자금은 나가지 않음
   → 데드라인 경과 시 누구나 실패 전환 트리거 → 비례 환불
```

- **IA (Information Architecture)**

```
FarmFi 웹                              FarmFi 앱 (운영자)
├── 랜딩                               ├── 로그인 · 매장 선택
├── 투자자                             ├── 대시보드 (오늘 할 일·알림)
│   ├── 프로젝트 목록 / 상세            ├── 운영 (생육 현황·베드별·재배 일정)

│   ├── 투자 신청                       ├── 연동 (재고·생산량)
│   └── 포트폴리오 · 수익 상세          └── 리포트 (매출·판매량·인기 품목)
```

#### 3.2. 기능설명

##### ` 투자 목록 / 상세 (웹) `
- 프로젝트 목록, 목표 금액·참여자 수·진행 단계, 보관 잔액, 마일스톤 타임라인, 체인 기록(트랜잭션 해시)
- 공개 문서 4종(핵심 안내서 · 임대차 계약서 요약본 · 마일스톤 집행 계획서 · 운영사 소개)을 PDF로 내려받기
- 문안은 고정 파일이 아니라 그 프로젝트의 실제 단계·집행액·에스크로 잔액으로 생성된다

##### ` 투자 신청 / 수익 상세 (웹) `
- 본인인증 게이트 → 투자안(연 프리미엄·회수기간) 확인 → 금액 선택(퀵버튼) → 신청 제출
- 이번 달 예상 회수액·회수 예정일, 산정 근거, 월별 회수 내역(지급완료·회수예정·지급실패), 내역 내보내기

##### ` 운영자 온보딩 (웹) `
- 개점 준비 대시보드(전체 준비도·개점 목표일) → 자격 확인·매장 배정 → 필수 교육 수강(진행률·이어듣기) → 현장 방문 → 운영보증서(VC) 발급 → 운영 계약 서명

##### ` 구독 / 픽업 (웹) `
- 지점 탐색 → 믹스팩 선택(3종·5종·7종) → 산출량 안에서 작물·드레싱 구성 → 결제 → 정기구독 관리(주기·다음 결제일·해지)
- 매장 수령 — 픽업 바코드 발급, 픽업 시간대 안내, 준비 완료 알림

##### ` 관리자 검증 콘솔 (웹) `
- 마일스톤 증빙 업로드 → AI 검증 실행 → 신호별 결과·교차검증 확인 → 단계 집행
- 항목마다 충족·미충족과 근거 증빙을 지정해야 승인 버튼이 열린다

##### ` 운영자 앱 (Expo React Native) `
- 다지점 중 운영 매장 선택, 대시보드(오늘의 할 일·알림)
- 운영 — 센서 가동률·오늘 수확 가능·이번달 수확량, 베드별 작물 생육률, 재배 일정 계획
- 모니터링 — 온도·습도·CO₂·EC 실시간 표시, LED·환기팬·급수 펌프 원격 제어
- 연동 — 생산량·재고를 매장 판매 데이터와 연동해 결품·과잉 방지
- 리포트 — 최근 30일 매출·판매량·주문수, 일별 매출 그래프, 인기 품목 TOP 3

##### ` 운영 대시보드 (웹) `
- 실시간 IoT 환경(온·습·CO₂·광량·pH), 생육 이상 감지·경고, ESG 임팩트, 온도 추이 차트

|라벨|이름|상세|
|:---:|:---|:---|
| F1 | 본인확인 | - OmniOne CX 표준인증창 호출(QR/딥링크) <br/>- 전자지갑 신분증 제출(eVP) → VC·Verifier 검증 <br/>- 실명·연령(성인)·투자한도 판별 |
| F2 | 투자 신청 | - 본인확인 완료자만 진입 <br/>- 연간 투자한도 초과 시 거부 <br/>- 투자안(연 프리미엄·회수기간) 선택 |
| F3 | 가상계좌 입금 | - 토스페이먼츠 가상계좌 발급 <br/>- 입금 통지 웹훅을 계좌별 `secret`으로 검증 <br/>- 같은 통지 3회에도 입금 이벤트 1건(멱등) |
| F4 | 구좌 발행 | - 입금 확인과 같은 트랜잭션에서 발행 예약 <br/>- Chain Relay가 운영지갑으로 서명·전송 <br/>- DB ↔ 체인 원장 대사 |
| F5 | 증빙 제출 | - 운영자·설비업체가 단계별로 업로드 <br/>- 원본은 Storage, SHA-256 해시를 함께 기록 |
| F6 | AI 증빙 검증 | - 신호별 판독(계약서·영수증·사진·검수확인서·센서) <br/>- 문서 간 교차검증 <br/>- 한 신호라도 실패하면 집행 불가 |
| F7 | 단계 집행 | - 검증 통과 + 관리자 항목 확인 후에만 집행 <br/>- 앞 단계 미완료 시 거부(순번 강제) <br/>- 에스크로 → 설비업체 직불 |
| F8 | 데드라인·환불 | - 단계마다 180일 기한 <br/>- 경과 시 누구나 실패 전환 트리거 <br/>- 미집행 잔여금 비례 환불 |
| F9 | 정산·수익 배분 | - 관리자가 매출·비용 확정해야 계산 시작 <br/>- 보유 구좌 비율대로 배분 <br/>- 지급 결과 체인 기록 |
| F10 | 생육 모니터링 | - 온·습도·CO₂·광량·EC 수집·시각화 <br/>- Z-score + 도메인 정상범위로 이상 판정 |
| F11 | 재고-생육 연동 | - 재고 상태와 작물 성숙 시점 연결 <br/>- 수확 대상·보충 필요 품목을 '오늘 할 일'로 |
| F12 | 구독·픽업 | - 믹스팩 3종·5종·7종 선택, 작물·드레싱 구성 <br/>- 픽업 바코드 발급, 같은 바코드 재처리 차단 |

#### 3.5. 개발 경과와 진행 증빙

**실제 동작 여부** — `납입 → 발행 → 증빙 → 검증 → 집행 → 정산 → 지급` 전 과정이 실제로 동작한다. `demo/reset`·`demo/step` 9단계로 통주행 시연할 수 있다.

| 구간 | 확인한 것 |
|:---|:---|
| 투자금 납입 | **토스페이먼츠**가 실제로 가상계좌를 발급한다(우리은행). 입금 통지 웹훅은 계좌별 `secret` 대조로 검증한다 |
| 보유 구좌 발행 | 입금 확인과 **같은 트랜잭션**에서 발행을 예약하고 Chain Relay가 체인에 올린다. **OmniOne Chain(BESU)에 920구좌 발행 확인** |
| 원장 대사 | DB 920구좌 ↔ 체인 920구좌, **불일치 0건** |
| 증빙 → 집행 | 실 Gemini로 계약서·영수증·사진을 교차검증하고, **증빙이 승인된 단계만** 자금이 나간다 |
| 정산 → 지급 | 관리자가 매출·비용을 **확정해야** 회수금 계산이 돈다. 지급은 어댑터를 타되 실제 이체는 지급대행 계약 전까지 Mock이며 화면에 그대로 표기한다 |

### 4. 설치 및 사용 방법

**필요 패키지** — 위의 사용기술 참고 (Node.js 20+, Git)

```bash
$ git clone https://github.com/PNU-2026-AI-Hackathon/pnuai-b-01-b301.git
$ cd pnuai-b-01-b301/frontend
$ npm install
$ cp .env.example .env          # DATABASE_URL, JWT_SECRET, GEMINI_API_KEY
$ npm run prisma:generate
$ npx prisma db push --url "<세션 pooler 5432 URL>"   # DB 스키마 반영
$ npm run seed                  # 시드 (지점·품목·재고·수확·판매·IoT·투자)
$ npm run dev                   # http://localhost:3000
```

> 스키마 반영(DDL)만 **세션 pooler(5432)** 로 해야 한다. `.env`의 `DATABASE_URL`은 트랜잭션 pooler(6543)라 `prisma db push`가 거기서는 통하지 않는다. 런타임과 시드(DML)는 6543 그대로 쓴다.

운영자 앱:

```bash
$ cd app && npm install && npx expo start
```

컨트랙트 빌드·테스트:

```bash
$ cd contracts && git submodule update --init && forge test
```

**시드 로그인 계정:** `operator@farmfi.test` / `admin@farmfi.test` (비밀번호 `farmfi123`)

**환경 변수:** 자세한 키 목록은 [CONTRIBUTING.md](CONTRIBUTING.md) 참고. 최소 구동은 `DATABASE_URL` · `JWT_SECRET` · `GEMINI_API_KEY`면 되고 온체인·본인인증 키가 없으면 해당 기능이 비활성으로 떨어진다.

신규 합류자는 [docs/service-plan.md](docs/service-plan.md)(기획 정본)를 먼저 읽고 [docs/spec/feature-spec.md](docs/spec/feature-spec.md)(웹)와 [docs/spec/app-feature-spec.md](docs/spec/app-feature-spec.md)(앱)로 기능 범위와 화면 흐름을 파악하면 된다.

### 7. 해커톤 참여 후기

- 이정서
  > 짧은 시간이었지만 스마트팜 산업을 깊이 들여다보고, 블록체인과 스마트컨트랙트의 활용 방안을 고민하면서 새로운 투자상품까지 직접 고안해 볼 수 있었습니다. 하나의 아이디어를 사회·경제·기술의 관점에서 구체화하며 많이 배우고 성장한 시간이었습니다.

- 조원진
  > UI/UX를 배워본 적은 있지만, 기획자, 개발자분들과 협업하는 것은 처음이라 제가 설계한 화면과 기능이 실제 개발 과정에서도 적절한지 확신이 서지 않아 고민했던 순간도 많았습니다.
  >
  > 여러 시행착오를 직접 겪으며 기획이 디자인으로, 디자인이 개발로 어떻게 연결되는지 몸소 배울 수 있었고, 클로드 MCP와 같은 새로운 도구를 활용하는 경험도 쌓을 수 있었습니다. 이 경험을 자양분 삼아 앞으로도 익숙하지 않은 분야더라도 두려워하지 않고, 도전하며 배우는 태도를 이어나가고 싶습니다.

- 우민성
  > 이번 해커톤을 통해 평소 접해보지 못했던 블록체인 기술을 실제 프로젝트에 적용해보는 경험을 할 수 있었습니다. 또한 AI를 단순히 사용하는 것을 넘어, AI와 함께 코드를 작성하고 수정하며 서비스를 구현하는 새로운 개발 방식을 경험할 수 있어 의미 있었습니다.

- 박태정
  > 규모 있는 서비스의 개발을 맡아 보며, 어려운 것은 기능을 만드는 일이 아니라 만들어 둔 기능들이 서로 어긋나지 않게 하는 일이라는 것을 배웠습니다. AI가 발전하면서 만드는 속도는 빨라졌지만 그만큼 결정하고 검증하는 능력이 더 중요해졌다고 느낍니다.
